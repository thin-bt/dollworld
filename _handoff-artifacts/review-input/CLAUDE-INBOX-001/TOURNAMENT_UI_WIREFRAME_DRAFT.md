- document: `TOURNAMENT_UI_WIREFRAME_DRAFT.md`
- status: `PROPOSED / NON-NORMATIVE UI DIRECTION`
- target: Sprint 2 tournament observation UI and subsequent common UI baseline
- authority rule: game rules, eligibility, schedule generation, participant selection, ranking, promotion, battle results, and canonical data remain owned by accepted specifications and runtime/API contracts. This document must not invent or override them.
- visual baseline: `S1_5_UI_MOOD_REFERENCE.html`
- structural baseline: `S1_5_UI_WIREFRAME_DRAFT_UPDATED.md`
- presentation baseline: `S1_5_UI_PRESENTATION_DIRECTION_IMPLEMENTATION_BIND_20260814.md`

## 0. Goal

大会を「内部処理結果」ではなく、観察ゲームとして追いやすい画面にする。

最低限、ユーザーが次を自然に追えることを目的とする。

1. いつ、どの大会が開催されるか
2. その大会に誰が参加するか
3. どのカテゴリ／ランク帯の大会か
4. 開催前・開催済み等の現在状態
5. 終了後に結果を確認できること
6. 人物詳細と大会を往復できること

Sprint 1.5で採用した「観察が主役、開発情報は副次」の方向を維持する。

## 1. Visual direction

`S1_5_UI_MOOD_REFERENCE.html` を大会UIのビジュアル基準として使用する。ただし完全コピーではない。

採用するもの:
- dark / quiet な背景
- 抑えたゲーム感
- 情報量が多くても読みやすい階層
- 重要情報をカード／見出し／状態表示で明確化
- 一覧は比較しやすい高密度
- 詳細画面は一覧より余白を持たせる
- 内部ID・hash・raw JSON等は通常画面の主役にしない

大会UIは、既存production UIを無条件にデザイン基準としない。新規大会UIを作るタイミングで、共通shell・一覧・詳細の見た目を必要に応じて同じ方向へ揃える。

「リッチ」とは装飾量ではなく、状態・重要度・開催時期・参加者比較・導線が一目で分かり、管理画面に見えないことを意味する。

## 2. Information architecture

最低限次の3画面を持つ。

```text
大会日程
  ↓
大会詳細
  ├─ 参加者一覧
  └─ 開催後：結果 / 対戦・記録への導線

参加者一覧 / 大会詳細
  ↓
人物詳細
```

将来、年間ランキング・大会史・重賞相当の大会・家系別大会成績などを追加できる構造にはしてよいが、現在authorityに存在しない機能を空タブやダミーで表示しない。

# 3. 大会日程表 UI

## 3.1 目的

「今年、どの月・どの週に、どのランク／カテゴリの大会があるか」を**年単位で一望**できるようにする。

月を1つずつ開いて確認するカレンダーではなく、育成・観察中に「次の大会はいつか」「このランク帯は今年どこにあるか」を視線移動だけで追える大会予定表を第一案とする。

Monster Farm 系の「週 × ランクを一覧できる大会表」の利点を取り入れる。ただし1か月単位に閉じず、dollworldでは**原則1年12か月を俯瞰できる構成**を優先する。

## 3.2 Primary layout — 年間大会マトリクス

第一候補:

```text
世界12年　大会日程                                      [前年] [今年] [翌年]

            1月                     2月                     3月                …
       1週  2週  3週  4週      1週  2週  3週  4週      1週  2週  3週  4週
S      ──   ──   ──   ◆       ──   ──   ──   ──       ──   ◆    ──   ──
A      ──   ◆    ──   ──       ──   ──   ◆    ──       ──   ──   ──   ◆
B      ◆    ──   ──   ──       ──   ◆    ──   ──       ◆    ──   ──   ──
C      ──   ──   ◆    ──       ◆    ──   ──   ──       ──   ──   ◆    ──
D      ──   ◆    ──   ──       ──   ──   ◆    ──       ──   ◆    ──   ──
E      ◆    ──   ──   ──       ──   ◆    ──   ──       ◆    ──   ──   ──
F      ──   ──   ◆    ──       ◆    ──   ──   ──       ──   ──   ◆    ──

◆を選択:
┌─────────────────────────────────────────────┐
│ 3月 第2週　A・Sオープン大会                │
│ 総合 / A・S共通　参加 16名　[開催前]       │
│                         [大会詳細を見る →]  │
└─────────────────────────────────────────────┘
```

実際の大会数・ランク構造・同週開催可否はauthorityに従う。UI上の例を仕様と解釈しない。

### 行

基本軸は大会の対象ランク／ランク帯。

例:
- S
- A
- B
- C
- D
- E
- F

A・S共通オープン、昇格大会、限定戦など単純に1ランクへ割り当てられない大会は、authority上の意味を壊さない形で以下のいずれかを採用する。

- 複数行をまたぐ表示
- `A/S` の共有行
- 補助行（例: 昇格 / 限定）
- セル内badge

どの方式にするかは実データ量を見て決めてよい。**同じ大会を別大会のように重複表示しない。**

### 列

- 1年12か月
- 1か月4週
- 合計48週

を一続きの時間軸として扱う。

月の境界は明確にするが、月ごとに画面・タブを分断しない。

## 3.3 年間俯瞰を優先する理由

この画面で重要なのは個々の大会説明より先に、

- 年間の大会密度
- ランクごとの開催間隔
- 次に出られそうな大会
- 限定戦や昇格戦がどこに挟まるか
- 現在週からどれくらい先か

を理解できること。

したがって、巨大な大会カードを12か月分縦積みする方式は第一案にしない。

## 3.4 セル表現

各大会セルはコンパクトにする。

セル内に常時すべての詳細を詰め込まず、最低限:

- 大会の存在
- 種別を判別する短い表示
- 状態が必要な場合のmark

程度にする。

大会名・参加人数・開催状態などの詳細は、

- hover / focus
- 選択時のpreview
- 大会詳細画面

のいずれかへ逃がしてよい。

ただしhoverだけに情報を依存させず、keyboard操作でも取得できること。

## 3.5 Category distinction

authorityに存在するカテゴリを視覚的に区別する。

例:
- 総合
- 格闘限定
- 剣技限定
- 魔法限定
- 昇格
- A/S open 等

色だけで区別しない。短い文字、記号、border/pattern、badge等を併用する。

## 3.6 Current time

現在の世界年月週は年間表の中で強く識別できるようにする。

例:

```text
                    ▼ 現在
4月              1週  2週  3週  4週
                     │
B      ──   ◆    ──   ──
```

現在週より過去・現在・未来の区別も読み取れるようにする。ただし過度に暗くして過去大会を読めなくしない。

## 3.7 Detail preview

大会セルを選択したとき、一覧性を壊さないサイズでsummaryを表示する。

```text
3月 第2週
A・Sオープン大会
総合 / A・S共通
参加 16名
開催前

[参加者] [大会詳細]
```

preview自体を巨大な右sidebarとして固定し、年間表を極端に狭くしないこと。

## 3.8 48週をどう収めるか

PC主対象なので、48週すべてを1画面に押し込んで文字を極小化することはしない。

第一候補:
- 12か月を4か月 × 3段、または6か月 × 2段の年間ブロックとして表示
- 各ブロック内ではランク行と週列を維持
- 同一ページ内で年全体を縦スクロールだけで追える

例:

```text
[ 1月 ][ 2月 ][ 3月 ][ 4月 ]
 S
 A
 B
 C
 D
 E
 F

[ 5月 ][ 6月 ][ 7月 ][ 8月 ]
 S
 A
 B
 C
 D
 E
 F

[ 9月 ][10月 ][11月 ][12月 ]
 S
 A
 B
 C
 D
 E
 F
```

これを**推奨初期案**とする。

1920px級の十分な横幅があり可読性が維持できる場合は6か月 × 2段などへ広げてよい。

避けるもの:
- 1か月だけ表示して「次月」を押さないと全体像が見えない
- 12か月を全部1行へ押し込み、セルが読めない
- 月ごとに巨大カードを並べて年間のランク比較ができない

## 3.9 Secondary views

必要なら同じcanonical dataから補助表示を作ってよい。

候補:
- `年間表`
- `直近大会`

ただし初期実装の主役は `年間表` とする。

`直近大会` はホームや大会画面上部の補助であり、年間表を置き換えない。

## 3.10 操作

最低限:
- 前年
- 現在年
- 翌年
- 大会セル選択
- 大会詳細
- 参加者一覧

filterを追加する場合も、年間全体の位置関係を崩さない。

## 3.11 Acceptance — schedule overview

大会日程UIは次を満たさない限り完了扱いにしない。

- 1年の大会予定を同一ページで俯瞰できる
- どのランク帯の大会がどの週にあるか追える
- 現在年月週の位置が分かる
- 月を切り替え続けなくても年間スケジュールを理解できる
- 大会を選択して参加者／詳細へ到達できる
- ランク・週の比較が、巨大カードや余白によって阻害されない
- 画面が単なるTournament DTOの縦一覧になっていない


# 4. 大会詳細 UI

## 4.1 目的

1大会について「何の大会で、いつ開催され、誰が出るか」を一画面で把握する。

## 4.2 Primary layout

```text
┌────────────────────────────────────────────────────┐
│ ← 大会日程                                         │
│                                                    │
│ 大会名                                             │
│ 世界12年 4月 第2週                                 │
│ 総合 / B級                         [開催前]         │
├───────────────────────┬────────────────────────────┤
│ 大会概要              │ 参加状況                   │
│ 種別       総合       │ 参加者 16名                │
│ 対象       B級        │ 定員   16名                │
│ 開催時期   4月第2週   │ [参加者を見る]             │
├───────────────────────┴────────────────────────────┤
│ 参加者                                             │
│  1. 人物名      B   24歳     ...          [人物]   │
│  2. 人物名      B   29歳     ...          [人物]   │
│  3. 人物名      B   21歳     ...          [人物]   │
│                                      [全員を見る]  │
└────────────────────────────────────────────────────┘
```

開催後は、sourceが存在する場合だけ優勝者・順位・大会結果・対戦記録への導線を追加する。

## 4.3 大会概要

通常画面で見たい情報:
- 大会名
- 世界年月週
- カテゴリ
- 対象ランク／出場帯
- 状態
- 参加人数
- 定員（canonical sourceがある場合）
- 開催結果（終了後、sourceがある場合）

TournamentId、scheduleOrdinal、hash、schemaVersion、internal receipt/proof、raw sourceなどは必要な場合のみ `開発者情報` 配下へ置く。通常画面の見出しにIDを出さない。

# 5. 大会参加者一覧 UI

## 5.1 目的

「誰が出る大会なのか」を比較して観察できるようにする。管理用entry tableではなく「出場者一覧」として見せる。

## 5.2 Layout

参加者一覧は **dense / compact table-first** とする。  
PCで横幅が余っても、各列を均等伸長してスカスカにしない。人物比較に必要な情報を1行へ凝縮し、1画面でできるだけ多くの参加者を見渡せることを優先する。

推奨イメージ:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│ 大会名 / 参加者 16名                                                        ← 大会詳細   │
├───┬────────────┬────┬───┬────────────────────────────┬───────────────┬──────────┤
│ # │ 人物       │級  │歳 │ 能力                       │ 適性          │ 戦績等   │
├───┼────────────┼────┼───┼────────────────────────────┼───────────────┼──────────┤
│ 1 │ 人物名     │ B  │24 │ 体75 力62 技81 速70 心68 魔55 │ 拳72 剣48 魔35 │ 8戦6勝   │
│ 2 │ 人物名     │ B  │29 │ 体69 力83 技71 速60 心77 魔22 │ 拳88 剣31 魔12 │ 9戦7勝   │
│ 3 │ 人物名     │ B  │21 │ 体57 力64 技92 速88 心66 魔40 │ 拳42 剣84 魔28 │ 6戦5勝   │
└───┴────────────┴────┴───┴────────────────────────────┴───────────────┴──────────┘
```

### Density rules

- 1参加者 = 原則1行。人物ごとに大きなカードへ分解しない。
- PCでは一覧本体の最大幅を無制限に広げない。広いviewportでも情報ブロックが間延びしない幅に収める。
- `# / Rank / 年齢` のような短い値は narrow column とする。
- 人物名も必要以上に横幅を取らない。
- 6能力は別々の巨大セルやカードにせず、**1つの比較ブロック内に横並びで詰める**。
- 3適性も同様にコンパクトな比較ブロックとする。
- 列間・セル内paddingは「管理画面のゆったりtable」より詰める。
- 行高を装飾目的で大きくしない。
- 行全体または人物名を人物詳細への主要導線にする。右端に毎行巨大な「詳細」ボタンを置いて余白を増やさない。
- hover / focus-visible は必要だが、hover時に行高やレイアウトを変えない。
- viewportが広い場合、余白はtable外側へ回し、セル間へばら撒かない。
- 一覧の情報密度は `S1_5_UI_MOOD_REFERENCE.html` の人物一覧以上を目安とし、横に広いだけの疎なtableを受入しない。

人物行はクリック／キーボード操作で人物詳細へ移動できる。

## 5.3 表示項目の優先順位

canonical/APIから安全に取れる場合:
- 人物名
- 現在ランク
- 年齢
- 大会との関係が分かるカテゴリ／適性
- 主要能力

人物一覧UIと同様、能力値は比較できるよう視認可能にする。6能力が現在の人物UIで表示対象なら、大会参加者一覧でも極端に情報を削らず比較可能性を保つ。

authority/APIに既に存在しており、追加計算なしで表示できる場合のみ:
- 年間戦績
- 年間ranking / points
- 直近大会成績
- 参加決定状態

「強さ予想」「勝率」「優勝候補」などの新規評価値をUI側で勝手に計算しない。

# 6. 状態別 presentation

### 開催前
- いつ開催か
- 誰が出るか
- カテゴリ／ランク帯
- 参加人数

### 参加者確定前
authority上まだ確定していない場合は「参加者はまだ確定していません」のような事実表示にし、予測参加者を生成しない。

### 終了後
- 優勝者 / 順位
- 大会結果
- 対戦記録への導線
- 人物詳細への導線

raw battle logsを大会TOPへ大量展開しない。

### 延期 / 取消
authority上の延期・取消情報がある場合のみ表示し、UIが日程変更を独自推測しない。

# 7. Common navigation proposal

候補:

```text
シミュレーション
人物
大会
模擬戦
イベント
```

navigation変更は現行UI authority / owning taskで正式採用された場合のみ行う。大会日程が主要観察対象になるため、採用する場合は「大会」を独立主要navigationにすることを第一候補とする。

# 8. Responsive policy

主対象はPC。参加者一覧はPCで比較しやすいtable-firstとする。

狭い画面では人物名・rank・年齢・主要能力を優先し、内部情報を先に削る。横幅不足を理由に主要能力を完全に見えなくしない。必要なら横スクロールまたは段階的レイアウトを使う。

# 9. Developer information

通常表示にはTournamentId、PersonId、schemaVersion、config/state/proof hash、raw canonical JSON、internal selection reason、allocation dataを前面に出さない。

受入・デバッグ上必要なものは既存方針と同様に二次的な `開発者情報` へ置く。ただしbrowser/API contract上公開が許可されている項目に限る。


# 10. 大会史 / 歴代結果 UI

## 10.1 目的

同じ大会シリーズについて、各開催回の優勝者・上位結果を時系列で追えるようにする。

単発の大会結果だけでなく、

```text
第1回 ○○大会　優勝：人物A
第2回 ○○大会　優勝：人物B
第3回 ○○大会　優勝：人物C
第4回 ○○大会　優勝：人物A
```

のように、大会そのものの歴史を観察できることを目的とする。

## 10.2 Information architecture

```text
大会日程
  ↓
大会詳細
  ├─ 今回の参加者
  ├─ 今回の結果
  └─ 大会史 / 歴代結果
         ↓
      第N回の大会結果
         ↓
      優勝者 / 上位順位 / 対戦記録 / 人物詳細
```

大会詳細から「歴代結果」へ自然に移動できること。

## 10.3 歴代結果一覧

推奨表示:

```text
┌──────────────────────────────────────────────────────────────┐
│ ○○大会　歴代結果                                [大会詳細へ] │
├──────┬──────────┬──────────────┬──────────────┬──────────┤
│ 回   │ 開催年   │ 優勝         │ 準優勝       │ 詳細     │
├──────┼──────────┼──────────────┼──────────────┼──────────┤
│ 12回 │ 世界12年 │ 人物A        │ 人物B        │ [結果]   │
│ 11回 │ 世界11年 │ 人物C        │ 人物A        │ [結果]   │
│ 10回 │ 世界10年 │ 人物D        │ 人物E        │ [結果]   │
│  9回 │ 世界 9年 │ 人物A        │ 人物F        │ [結果]   │
└──────┴──────────┴──────────────┴──────────────┴──────────┘
```

一覧は新しい開催回を上にすることを第一候補とする。

ただし「第N回」という正式な回次をcanonical dataが持たない場合、UIが独自に連番を生成して正本化しない。
その場合は世界年・開催日などauthorityに存在する識別情報を使う。

## 10.4 必須表示候補

canonical/APIに存在する範囲で:

- 大会シリーズ名
- 開催回または開催年
- 開催年月週
- 優勝者
- 準優勝者 / 上位順位（sourceがある場合）
- 大会結果への導線
- 優勝者人物詳細への導線

保持期間を超えた大会について、UIが過去結果を推測・復元しない。

## 10.5 大会結果詳細

1開催分の結果ページでは、sourceがある範囲で:

- 大会名
- 開催年・月・週
- 優勝者
- 順位
- 参加者
- 対戦結果
- 重要対戦ログへの導線
- 人物詳細への導線

を表示する。

大量のraw battle logを最初から展開せず、「大会結果 → 必要な対戦を見る」の順にする。

## 10.6 大会史の見せ方

大会史は単なるdatabase一覧ではなく、

- 連覇
- 同一人物の複数回優勝
- 世代交代
- 長期間の大会の流れ

を目で追いやすい密度にする。

ただし「連覇」「最多優勝」等の集計値を表示する場合は、canonical/APIまたは正式に許可されたpresentation集計が必要。
このUI文書だけを根拠に新しい記録計算を実装しない。

## 10.7 Acceptance

大会史UIは最低限:

- 同じ大会シリーズの過去開催を一覧できる
- 各開催の優勝者が一目で分かる
- 優勝者から人物詳細へ移動できる
- 各開催結果へ移動できる
- 回次がcanonicalにない場合にUIが勝手な「第N回」を事実として作らない
- 大会結果保持範囲を超える情報を捏造しない

こと。



# 11. 年間ランキング UI

## 11.1 目的

その世界年に「誰が年間を通して強かったか」を一画面で追えるようにする。

大会単発の結果ではなく、年間競技成績の総覧として扱う。

## 11.2 Layout

第一候補は高密度table。

```text
世界12年 年間ランキング                                [前年] [今年] [翌年]

┌────┬────────────┬────┬────────┬────────┬────────┬──────────┐
│ 順 │ 人物       │級  │ Points │ 出場数 │ 優勝数 │ 年間戦績 │
├────┼────────────┼────┼────────┼────────┼────────┼──────────┤
│  1 │ 人物A      │ S  │  1280  │   8    │   4    │ 15勝2敗  │
│  2 │ 人物B      │ A  │  1170  │   9    │   3    │ 14勝4敗  │
│  3 │ 人物C      │ A  │  1095  │   7    │   2    │ 12勝3敗  │
└────┴────────────┴────┴────────┴────────┴────────┴──────────┘
```

年間ランキングの基本表示項目は次とする。

- 順位
- 人物
- 競技ランク
- 年間ポイント
- 出場大会数
- 優勝数
- 公式戦勝敗

これらは canonical/API または accepted annual record projection から取得する。
UI側でログを走査して独自集計したり、独自の年間評価値を作らない。

## 11.3 Density

- 1人物=原則1行
- 順位・rank・数値列はnarrow
- 人物名は必要以上に伸ばさない
- wide viewportでも各列を均等伸長しない
- 余白はtable外へ逃がす
- 1画面で上位層を十分見渡せる密度にする

## 11.4 Interaction

最低限:

- 年切替
- 人物詳細へ移動
- 必要ならその人物の年間大会結果へ移動

並び順は canonical ranking order をそのまま使う。
UIが独自sortして公式順位と見た目を食い違わせない。

## 11.5 Acceptance

- 年間順位が一目で分かる
- 上位人物を比較できる
- 順位の根拠として表示可能なcanonical情報が近接している
- admin tableのように間延びしない
- current yearと過去年を切り替えられる
- 人物詳細へ自然に遷移できる


# 12. 大会組み合わせ / 結果 UI

## 12.1 目的

大会の組み合わせと試合結果を「見る」ための画面。

Sprint 2で扱う大会形式に合わせ、少なくとも次の2種類を別presentationとして用意する。

1. **総当たり / standings形式**
2. **トーナメント / knockout形式**

ユーザーが組み合わせを編集したり、勝敗を操作したりする画面ではない。

---

## 12.2 総当たり大会 UI

### 12.2.1 目的

全参加者の対戦結果と最終順位を一画面で比較できるようにする。

第一候補は、**順位表 + 対戦結果matrix** の組み合わせ。

### 12.2.2 順位表

```text
○○大会　総当たり結果

┌────┬────────────┬────┬────┬────┬────────┐
│ 順 │ 人物       │ 勝 │ 敗 │ 他 │ 成績等 │
├────┼────────────┼────┼────┼────┼────────┤
│  1 │ 人物A      │  4 │  1 │  0 │ ...    │
│  2 │ 人物B      │  3 │  2 │  0 │ ...    │
│  3 │ 人物C      │  3 │  2 │  0 │ ...    │
└────┴────────────┴────┴────┴────┴────────┘
```

表示する列はcanonical/APIに存在するものだけを使う。

最低限:
- 順位
- 人物名
- 勝敗またはstandings判定に使われる表示可能な成績
- 人物詳細への導線

同率順位の解消理由を通常画面で過剰に表示しない。
必要なら二次的な詳細へ置く。

### 12.2.3 対戦結果matrix

参加人数が視認可能な範囲なら、誰が誰に勝ったかを一覧できるmatrixを第一候補とする。

```text
        A   B   C   D   E
A       -   ○   ×   ○   ○
B       ×   -   ○   ○   ×
C       ○   ×   -   ○   ×
D       ×   ×   ×   -   ○
E       ×   ○   ○   ×   -
```

各セルは必要に応じて対戦詳細へ遷移できる。

○/×等の記号だけで情報を確定せず、
accessibility上必要なlabelを持たせる。

参加人数が多すぎてmatrixが読めない場合は、
round list / 対戦一覧へ切替えてよい。

### 12.2.4 総当たり visual rule

- standingsと対戦結果を離しすぎない
- 順位表を巨大カード化しない
- matrixはセルを大きくしすぎず、比較密度を優先する
- 人物名の見出しが長い場合でもmatrix本体を極端に圧迫しない
- current winner / top rankは色だけでなく順位・weight・icon等でも示す
- internal groupId / tiedSetHash等を通常画面に出さない

---

## 12.3 トーナメント大会 UI

### 12.3.1 目的

誰と誰が当たり、誰が勝ち上がり、最終的に誰が優勝したかを視線で追えるようにする。

### 12.3.2 Knockout bracket

第一候補:

```text
第1回 ○○大会

1回戦             準決勝              決勝

人物A ─┐
       ├─ 人物A ─┐
人物B ─┘         │
                 ├─ 人物D ── 優勝
人物C ─┐         │
       ├─ 人物D ─┘
人物D ─┘
```

各matchにはsourceがある範囲で:

- 対戦者
- 勝者
- 決着種別
- score / 判定等
- 対戦詳細への導線

をコンパクトに表示する。

### 12.3.3 トーナメント visual rule

- bracketは横に無制限拡張しない
- 参加人数が多い場合はround単位で視認性を維持する
- 名前・勝者・次roundへの流れを最優先
- internal slot IDやMatchIdは通常画面の主役にしない
- 勝者は色だけでなく太字・icon・line等でも識別する
- 未実施matchと終了matchの区別を明確にする
- 大人数時に巨大な横スクロール一本へ逃げない

---

## 12.4 Format selection

UIはcanonical tournament formatに従って表示方式を切り替える。

```text
round-robin / standings → 総当たりUI
knockout               → トーナメントUI
```

実際のenum名・format field名はcurrent authority/APIに従う。

UI側でformatを推測しない。
formatを判別するbrowser-safe fieldが存在しない場合は
`UPSTREAM UI DATA CONTRACT REQUIRED` として戻す。

---

## 12.5 Interaction

どちらの形式でも最低限:

- 大会詳細へ戻る
- 対戦詳細を見る
- 人物詳細を見る

操作は閲覧のみ。
再抽選、手動組替え、勝敗入力などはauthorityに存在しない限り置かない。

---

## 12.6 Acceptance

### 総当たり

- 最終順位が一目で分かる
- 各人物の勝敗を比較できる
- 誰が誰に勝ったか追える
- 必要な対戦詳細へ到達できる
- standingsとmatch結果が矛盾して見えない
- 大きすぎる表や余白で比較性を失わない

### トーナメント

- 誰と誰が当たり、誰が勝ち上がったか追える
- 最終優勝者まで視線で辿れる
- 各試合の詳細へ到達できる
- 横スクロールだけに依存した巨大bracketにしない

### 共通

- canonicalな大会形式をUI都合で別形式にしない
- admin/debug画面に見えない


# 13. 昇格結果 / 人物ランク履歴 UI

## 13.1 目的

大会結果によって人物の競技ランクがどう変化したかを、人物の競技人生として追えるようにする。

新しい独立管理画面を増やすのではなく、主に次の2箇所で見せる。

1. 大会結果画面の昇格結果
2. 人物詳細画面のランク履歴

Sprint 2 authority上の昇格結果だけを表示し、UI側で昇格条件や判定を再計算しない。

---

## 13.2 大会結果画面の昇格表示

昇格大会や、authority上その大会結果によって昇格が確定した場合は、通常の順位・優勝表示に加えて昇格結果を近接表示する。

例:

```text
○○昇格大会　結果

優勝　人物A
2位   人物B
3位   人物C

昇格
人物A   B → A
人物B   B → A
```

実際の昇格人数・対象順位・条件はcanonical result/APIに従う。

UIが「この順位なら昇格のはず」と推測しない。

A→Sが大会単発優勝ではなくオープン実績認定等の別契約で決まる場合も、確定済みcanonical resultがあるときだけ表示する。

---

## 13.3 人物詳細のランク履歴

人物詳細に、競技ランクの変遷を時系列で確認できる領域を持つ。

ランク履歴は正式な長期保存対象とし、current rankから後付け再構成しない。

第一候補:

```text
ランク履歴

世界 8年   F → E   ○○昇格大会
世界10年   E → D   ○○昇格大会
世界13年   D → C   ○○昇格大会
世界16年   C → B   ○○昇格大会
```

sourceがある場合は:

- 世界年 / 月 / 週
- 変更前ランク
- 変更後ランク
- 根拠となった大会または認定
- 大会結果への導線

を表示する。

## 13.4 Presentation rules

- 現在ランクを人物詳細の主要情報として分かりやすく表示する
- ランク履歴はtimelineまたは高密度listでよい
- 1件ごとに巨大カード化しない
- `F → E` のように変化が一目で分かる
- 大会名または根拠から該当大会結果へ戻れる
- internal promotion receipt / hash / boundary dataは通常表示しない

## 13.5 大会日程との連携

昇格大会がcanonical上識別可能なら、年間大会日程表でも通常大会と区別できる表示を持つ。

ただし色だけに依存しない。

例:

```text
昇
```

や短いbadgeを利用してよい。

日程表から昇格条件そのものを長文表示する必要はない。
詳細は大会詳細へ送る。

## 13.6 年間ランキングとの関係

年間ランキング表にはcurrent rankを表示可能な場合は併記する。

ただし年間ranking orderとrank昇格は別概念として扱う。
UI上で「年間順位 = rank」と誤解させない。

## 13.7 Acceptance

最低限:

- 大会結果から誰が昇格したか分かる
- 人物詳細で過去のrank変遷を追える
- rank変化の根拠となった大会／認定へ移動できる
- current rankと年間rankingを混同させない
- UIが独自にpromotion判定を再計算しない
- canonicalに履歴データがない場合は架空の履歴を生成しない



# 14. 大会名 / 恒例大会の扱い

## 14.1 基本方針

すべての大会は、プレイヤー向けの表示名を持つ。

例:

```text
春風杯
銀月杯
王都武闘祭
蒼天剣技杯
紅蓮魔術祭
```

大会名は単なる装飾ではなく、年間日程・大会詳細・大会結果・過去大会一覧で共通して表示する。

## 14.2 TournamentIdとの分離

```text
TournamentId = 1回の開催を一意に識別するID
大会名       = プレイヤー向け表示名
```

同名大会が別年に開催されてもTournamentIdは別になる。

## 14.3 恒例大会

通常大会・限定大会・A/Sオープン等は、固定名の恒例大会として毎年同名を再利用してよい。

例:

```text
世界12年 春風杯
世界13年 春風杯
世界14年 春風杯
```

ただし、同名だからといって自動的に「大会シリーズ」としてcanonicalに束ねる必要はない。

過去大会は、開催年・カテゴリ・ランク・大会名等から検索/閲覧できればよい。

## 14.4 シリーズ扱い

正式にシリーズとして束ねるのは、制度上の継続性が必要なものに限定する。

第一対象:

- 公式昇格戦

例:

```text
B→A 公式昇格戦
```

公式昇格戦では必要に応じて歴代結果・昇格者を同種大会として追える。

通常大会については、表示名の一致だけを根拠にシリーズIDを作らない。

## 14.5 決定性

大会名はUIの実行時ランダム生成にしない。

同じsimulation / same-seed / same scheduleなら、同じ大会に同じ表示名が割り当たるよう、accepted authority側で決定的に割り当てる。

大会名の候補集合・割当規則の正式な所有先はcanonical implementation/spec authorityで決める。

UIは名前を生成せず、渡されたdisplay nameを表示するだけとする。

## 14.6 Acceptance

- 全大会にプレイヤー向け大会名が表示される
- 同じ開催大会で画面ごとに名前が変わらない
- same-seedで大会名割当が変動しない
- 通常大会を表示名だけで勝手にseries化しない
- 公式昇格戦は必要に応じて同種開催として歴代結果を追える

# 15. Future extension reserve

今は実装しないが、後から追加しやすくする対象:
- 大会grade / prestige
- 賞金
- 家系別大会実績
- 流派別大会実績
- 大会記録
- 最高位大会

空タブ、disabled menu、coming soon表示は作らない。


## 15.7 Read freshness / cache rule

Tournament observation UI must not assume that every page is fetched or cached with the same policy.

Use the source mutability rules defined in `SPRINT2_UI_DATA_CONTRACT_GAP_MAP.md`.

Examples:
- completed tournament result: persistent immutable cache allowed
- past annual ranking: cache after year finalization
- current annual ranking: invalidate on competitive updates
- in-progress tournament: invalidate on tournament updates
- current person detail: live/current-state policy

Cache is a presentation optimization, never canonical truth.
A missing cache must always be reconstructable from accepted source data.


# 16. UI data contract preflight

Before implementation/acceptance of the Sprint 2 observation UI, read:

`SPRINT2_UI_DATA_CONTRACT_GAP_MAP.md`

Any UI-required value that cannot be supplied by an accepted canonical source or browser-safe read projection must be classified as:

`UPSTREAM_UI_DATA_CONTRACT_REQUIRED`

Do not make the browser reconstruct tournament domain logic from raw internal state.

The Sprint 2 completion path must explicitly resolve or user-defer the gap map items before product-visible completion.

# 17. Implementation guard

大会UI着手時に最低限次を実装担当が直接読む。

1. current accepted tournament / Sprint 2 authority
2. `TOURNAMENT_UI_WIREFRAME_DRAFT.md`
3. `S1_5_UI_WIREFRAME_DRAFT_UPDATED.md`
4. `S1_5_UI_MOOD_REFERENCE.html`
5. `S1_5_UI_PRESENTATION_DIRECTION_IMPLEMENTATION_BIND_20260814.md`

`S1_5_UI_PRODUCT_DIRECTION_ADDITION_DRAFT_UPDATED.md` は将来構想の背景資料であり、current Sprintに未採用の機能を実装する根拠にはしない。

着手前に上記ファイルが実装側から実際に取得可能であることを確認する。

# 18. Acceptance direction

大会UIの受入では「データが表示できる」だけで完了にしない。

参加者一覧については、**横幅が広いだけで情報が疎なtable、1人ごとの過大な余白、大きすぎる行高、能力値が離れすぎて比較しづらいlayoutはNG** とする。  
PCの広い画面では「広げる」のではなく、比較対象を近づけた高密度一覧として成立していることを確認する。

最低限:
- 大会日程が世界の競技カレンダーとして読める
- 現在時点と開催予定が分かる
- 大会詳細へ自然に移動できる
- 参加者を比較できる
- 人物詳細へ自然に移動できる
- 開催済み大会は結果へ到達できる
- internal/admin DTO viewerに見えない
- `S1_5_UI_MOOD_REFERENCE.html` より明らかに貧弱なpresentationで完了扱いにしない
- keyboard操作、focus-visible、状態の非色依存を維持する

最終的なユーザー向け見た目は、ユーザーによる画面確認を受入の一部とする。

# 19. Authority boundary

この文書はUI proposalであり、以下を決定しない。

- 大会開催ルール
- 開催月・週
- 定員
- 参加資格
- 人物AIの出場判断
- 選抜priority
- bracket生成
- 大会順位計算
- promotion
- ranking point
- postponement / cancel rules
- highest championship rules
- battle rules

表示に必要なcanonical field/APIがない場合、UI側で推測・再計算・仮フィールド追加を行わず、`UPSTREAM UI DATA CONTRACT REQUIRED` として戻す。

```text
  → 大会詳細

```

を初回実装の最小完成形とする。
