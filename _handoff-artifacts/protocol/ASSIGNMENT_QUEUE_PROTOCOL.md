## QUEUE-FAST-001 — compact polling
Normal PM run:
1. read `audit/assignments/PM_EXECUTOR.md`; if this runtime is not the active executor, do not perform PM-owned writes and exit the PM write path;
2. enumerate the non-terminal PM-request inbox governed by `ARTIFACT-PM-REQUEST-001`; process every new `PENDING` request and re-evaluate non-terminal `DEFERRED` / `NEEDS_USER_INPUT` requests when their `resume-watch` may have changed, a superseding request exists, or their exact resume condition is already satisfied by live controls read in this run; enumeration/read completeness follows `QUEUE-READ-COMPLETENESS-001`. Enumeration/classification may precede the ordinary lane scan, but any request that can dispatch, redirect, stop, cancel, or supersede a lane must trigger a fresh targeted read of that lane's canonical CURRENT/OUTBOX or Inbox/Active before mutation;
3. Role1 CURRENT + OUTBOX
4. Role2 CURRENT + OUTBOX
5. Role3 CURRENT + OUTBOX
6. Cursor A/B2 Inbox/Active are conditional reads, not unconditional polling. PM may omit a fresh Cursor lane read only when the compact controls already read in the current run are sufficient to prove that the omitted Cursor lane cannot change any mandatory transition, release/assignment decision, refill choice, pickup/recovery action, Sprint/final-verification decision, or safe next-task dispatch in this run. When PM cannot prove that non-impact from current evidence, it must fresh-read the relevant Cursor Inbox/Active before reaching the drain fixed point. If PM reports a Cursor lane as not read, the report must state the concrete non-impact reason; generic phrases such as `not required this pass` or `Role control drain prioritized` are insufficient by themselves.
For Cursor B2 executor-health classification, the production pickup authority is the 5-minute SDK executor path. PM must use `CURSOR_EXECUTOR_DAEMON_HEARTBEAT.md` and `CURSOR_B2_EXECUTOR_HEARTBEAT.md` as the primary heartbeat evidence for B2 pickup/execution health. `CURSOR_B2_LOOP_HEARTBEAT.md` belongs to the legacy chat-bound 1-hour tick loop and, by itself, must not classify B2 as stopped or `CURSOR_TICK_LOOP_STALL`. A fresh parent/agent heartbeat or `processAlive: true` is not sufficient proof that the substantive verification child process is still progressing. While B2 reports `INVOKING`/equivalent active execution for a long-running command, the authoritative health surface must expose, when a child process exists, the active child PID/process identity plus a task-scoped `lastProgressAt` (or equivalent monotonically updated progress timestamp/event). PM may classify the task as substantively active only when that child/process evidence is live and progress evidence is fresh for the task's declared long-run profile; parent-only liveness with stale task progress is `B2_PROGRESS_UNPROVEN` and must trigger bounded executor/progress recovery rather than indefinite ACTIVE reporting. If the SDK daemon heartbeat is fresh and the task-scoped child/progress evidence is also live/fresh, report B2 as active even when the legacy 1-hour heartbeat is stale. If a PREPARED B2 task remains unclaimed while SDK daemon heartbeat is fresh, classify the issue as SDK scheduling/polling/pickup delay and inspect A/B2 concurrency rather than inferring daemon death. Only stale/missing authoritative SDK heartbeat, explicit SDK executor failure, or stale/missing required child/progress evidence during claimed substantive execution supports an SDK-executor/progress-stall classification.
An item-scoped read/write/parse failure, blocker, or malformed request does not end the PM scan; apply `QUEUE-LOCAL-ISOLATION-001` and continue independent lanes/requests that remain safe.
Before exit, every discovered mandatory transition must be closed: a new `PENDING` request, due/satisfied `resume-watch`, a terminal OUTBOX whose result exposes a uniquely executable next action or a still-required machine-observable watch, consumed PREPARED command, terminal request still physically in inbox, or other already-determined control transition must either be applied/read back or carry an exact retry/blocker. A terminal OUTBOX paired with the same generation still named by CURRENT is not by itself a mandatory mutation: under `CORE-STATE-001` that generation is consumed, and when no concrete next assignment/watch exists the lane may rest without minting a transport-only generation. Apply `QUEUE-WATCH-POLL-001`, `QUEUE-REQUEST-LIFECYCLE-001`, and `QUEUE-FAIRNESS-001`; silently leaving a discovered mandatory transition untouched is invalid and becomes a `QUEUE-STALL-RECOVERY-001` candidate.
If unchanged and no executable safe action or mandatory transition exists, exit. Exception reads follow CORE-READ-001.

Normal Role automation begins with its own CURRENT + OUTBOX. A CURRENT generation/state that is newer than the represented OUTBOX is not an idle fast path; apply `QUEUE-RECONCILE-001`. Before normal exit, apply the compact asynchronous Cursor/B2 terminal relay check from `QUEUE-CURSOR-RESULT-RELAY-001`.

**In-run read dedupe / fast-path discipline.** Within one run, an actor must not re-read the same stable control merely for reassurance. A second read of the same stable identity is justified only when (a) this run mutated that control and readback is required, (b) another actor may have changed it after the first read and a pending decision materially depends on the fresh value, (c) `QUEUE-PM-DRAIN-001` requires a targeted re-scan after an actual mutation, or (d) a concrete parse/transport ambiguity requires recovery. Full-rule, Roadmap, Activity-history, old evidence, and broad Drive/search reads remain exception reads under `CORE-READ-001`. A same-generation terminal Role fast path must not expand into audit/evidence/rule-owner rereads unless a new assignment, score-recovery/failover suspicion, control mismatch, or other explicit trigger requires them. Performance logging under `ACTIVITY-RUN-PERF-001` is written once at run end and must not cause additional control reads.
If CURRENT and OUTBOX have the same assignment-key/generation and OUTBOX already contains the terminal result for that generation (`RESULT_READY` or equivalent final result), the Role must not re-run or re-report inability to continue solely because stale CURRENT still says `READY`. Treat that generation as already consumed from the Role side and perform no duplicate substantive work. Before any `NO_ACTION` exit, the Role must apply the bounded autonomous convergence check in `QUEUE-ROLE-AUTONOMY-001`, including any eligible pre-authorized continuation under `QUEUE-ROLE-CONTINUATION-001`. PM performs the bounded next-work/watch check required by `QUEUE-PM-DRAIN-001` only for transitions not already converged by that Role path; cosmetic CURRENT normalization is optional. Only a newer generation, an eligible deterministic continuation, or an explicit distinct rework assignment may reopen execution.

## QUEUE-RUN-PERF-001 — lightweight run-phase performance accounting
PM / Role1 / Role2 / Role3 automation runs measure coarse wall-clock elapsed time without instrumenting individual tool calls. Use the runtime clock already available to the run; performance accounting must never delay substantive work, trigger a broad search, or require a control reread.

Capture one run summary with these non-overlapping coarse wall-clock buckets where applicable: `control-read`, `rule-resolution`, `decision`, `substantive-work`, `write-readback`, `score-failover`, and `total`. A wall-clock interval belongs to at most one phase bucket; do not double-count the same interval across phases. `total` is the end-to-end elapsed time and may include small unclassified runtime overhead, but the sum of named phase buckets must not exceed `total` except for coarse rounding. Also record `read-count`, `same-control-reread-count`, `exception-read-count`, `write-count`, run class `NO_ACTION | CONTROL_ONLY | SUBSTANTIVE`, and execution mode `PM | ROLE | SURROGATE_PM`. A Role run that acquires a PM failover lease records `mode=SURROGATE_PM` so its timing is not compared as an ordinary Role sample. If a phase is not applicable, record `0`; do not manufacture precision unavailable to the runtime.

**Terminal Role NO_ACTION fast path.** When the actor is Role1/Role2/Role3 and the first CURRENT+OUTBOX read proves the same assignment-key/generation is already terminal-consumed, no valid newer fallback/overlay is exposed, no eligible `continuation-authority` exists under `QUEUE-ROLE-CONTINUATION-001`, and no explicit reconciliation, audit, score-recovery/failover suspicion, autonomous-watch/result-recovery action, or asynchronous Cursor-result relay trigger is present, classify the substantive path as `NO_ACTION`. In that path, do not re-resolve or reread full rule-owner bodies merely to reconfirm unchanged semantics. Use the already-routed Rule IDs and the compact controls needed for PM scoring/failover/relay only; broader Activity/history, Roadmap, evidence, and owner-file reads remain exception reads and require a concrete trigger. This fast path never suppresses `ACTIVITY-PM-SCORE-001`, `QUEUE-PM-FAILOVER-001`, `QUEUE-CURSOR-RESULT-RELAY-001`, monotonic readback after a write, or any implementation-audit root entry requirement when an actual audit assignment is live.

The summary is appended once at run end under `ACTIVITY-RUN-PERF-001`. It is diagnostic evidence only and never changes authority, verdict, acceptance, or PM score. Activity write failure remains non-blocking under `ACTIVITY-FAIL-001`.

Fast-path targets are diagnostic thresholds, not correctness deadlines: `NO_ACTION` <=120s, `CONTROL_ONLY` <=180s excluding provider/tool outage time, while `SUBSTANTIVE` has no fixed ceiling because bounded audit/readiness work may legitimately take longer. A run exceeding a target records `PERF_SLOW` with the longest phase and concrete cause when observable. Provider/tool wait, required independent audit work, and required verification are separated from suspected avoidable overhead.

After at least 3 recent samples exist for the same actor and run class, PM may use the latest 5 samples for bounded performance diagnosis. Treat repeated same-control rereads, exception reads without a trigger, repeated terminal-generation reevaluation, full Activity/history mining, broad evidence rereads, or duplicated rule-resolution work as suspected waste. Safe optimization means removing/reordering those redundant reads while preserving audit entry rules, monotonic/readback fencing, PM fixed-point closure, failover fencing, and independent acceptance. Performance diagnosis itself must not become a mandatory blocker for development.

## QUEUE-PM-DRAIN-001 — PM internal-action drain before report/idle
Every active PM run, including a user-triggered `k` / `ｋ` run and the scheduled PM automation, must reach a bounded **internal fixed point** before it may report idle/waiting or end normally. The execution order is mandatory: **READ live controls -> CLASSIFY mandatory transitions -> APPLY all safe PM-owned mutations -> READ BACK every mutated control -> RE-SCAN for newly exposed mandatory transitions -> repeat until one complete pass produces no additional safe PM action -> REPORT**. User-visible reporting is forbidden before this fixed point.

Status reads, narrative planning, scheduler edits, wake/re-anchor operations, and automation `last_run_time` changes do not by themselves count as PM drain progress. If a terminal OUTBOX exposes a uniquely executable next assignment/watch, or a consumable Cursor result, stale PREPARED state, `FAILED_NO_PROGRESS` lane, or any other safe mandatory PM-owned transition remains after a scan, PM continues execution instead of reporting. A same-generation terminal OUTBOX with no concrete next work is a coherent consumed/resting boundary and does not require a control write merely to make CURRENT look idle. A run may end without a PM-owned mutation when a fresh final scan proves that no safe mandatory PM action exists.

A PM-owned action is still internally executable when the current authoritative controls uniquely determine it and the active PM has the required ownership/capability to perform it. This includes, when applicable: reconciling stale terminal CURRENT/Inbox state; processing/re-evaluating PM requests; converting a satisfied wait into executable work; issuing the next safe Role/Cursor assignment; completing post-dispatch wake under `QUEUE-DISPATCH-WAKE-001`; repairing a uniquely mechanical PM-owned control under `QUEUE-CONTROL-RECOVERY-001`; applying a required material `PROJECT_ROADMAP.md` update under `CORE-ROADMAP-001`; and following any newly created mandatory transition exposed by those actions. When a Cursor A/B2 Inbox is `PREPARED` while its Active control is `IDLE` or otherwise has not claimed that task, the drain applies `CURSOR-PICKUP-001` before treating the lane as waiting or performing a wake; publication-integrity repair required by `CURSOR-PUBLISH-001` is a PM-owned same-run action.

PM must not label its own still-executable action as `UPSTREAM`, `WAITING_UPSTREAM`, `user wait`, or an external blocker merely because another actor cannot proceed until PM acts. Actor dependency is not the same as an external dependency. A wait is valid only after the bounded fixed-point pass proves that no safe PM-owned action can remove that wait and the exact remaining dependency belongs to the user, another runtime currently executing owned work, external/provider state, missing higher authority, or another genuinely non-PM condition.

A PM run is invalid if it ends with any already-observed safe PM-owned transition merely described as a next action. Reporting is after action closure, not a substitute for it. If tool/run budget prevents one remaining safe PM action, `QUEUE-RUN-BUDGET-001` prioritizes that authoritative mutation over optional narration/hygiene; if the action still cannot be completed, record the exact attempted action and concrete blocker/retry condition rather than a generic wait.

**Terminal consumption / next-work postcondition.** A terminal Role OUTBOX consumes the matching CURRENT generation under `CORE-STATE-001`. PM does **not** mint a new generation merely to carry `IDLE`, `TERMINAL`, `WAITING`, the already-proven verdict, or an absence of work.

Before normal run completion, PM performs one bounded next-work check for every terminal Role result that is not yet superseded by a newer executable CURRENT generation. `newly observed` is only a fast-path optimization and never an eligibility condition: if a prior PM run missed refill/watch publication, every later active PM run must recover that omission. When the consumed CURRENT carries eligible `continuation-authority`, PM first applies `QUEUE-ROLE-CONTINUATION-001`: it adopts or publishes the same deterministic successor identity, or proves a newer canonical authority invalidates that continuation, before considering any different N+1 command.
- if that result or current authority exposes a distinct safe executable next assignment for the same Role, publish/read back that next READY generation in the same drain cycle;
- if a genuine machine-observable dependency must be watched and keeping an explicit Role wait materially improves routing, PM may publish/read back a WAITING generation with the exact blocked scope/resume-watch;
- if no distinct safe work or useful watch exists, leave the consumed CURRENT/terminal OUTBOX pair as-is and classify the lane as resting/terminal-consumed. This is successful drain, not `REFILL_MISSED`.
- if the terminal result itself names a concrete `next-work`, next family, acceptance-preflight, or other bounded follow-on and current authority still permits it, PM must either dispatch that follow-on or record the exact authority/collision reason it is no longer safe. Merely being older than the current run does not make the transition disappear.
- when a terminal-consumed lane with concrete safe follow-on survived one or more PM runs without dispatch, classify the repair as `REFILL_MISSED_RECOVERY`, perform the dispatch in the current drain, and do not mint an extra transport-only generation before the real work generation.

After any actual next-generation mutation, PM still fresh-reads the stable CURRENT ID and proves the intended command was published. Capability/tool failure matters only when a concrete required next command exists; absence of a transport-only refill is never a failure.

The drain is bounded and non-speculative: it does not authorize busywork, new product semantics, duplicate generations, overriding an actor-owned Active/OUTBOX, or inventing roadmap scope. Stop when a full compact pass reveals no new mandatory or uniquely authorized PM action.

## QUEUE-PM-SELF-WAKE-001 — bounded PM asynchronous follow-up self-wake
The dollworld PM loop keeps `FREQ=HOURLY` as its base scheduled cadence, but an hourly poll is not allowed to turn a PM-created short asynchronous handoff into an avoidable one-hour blind spot. After `QUEUE-PM-DRAIN-001` and the final fresh reconciliation pass, PM must decide whether the just-finished run left a **machine-observable asynchronous transition that PM itself newly dispatched, retried, recovered, or materially advanced and whose outcome is not yet consumable**. When yes, PM must perform a bounded self-wake eligibility check and, when eligible, re-anchor the same PM automation to a short follow-up slot instead of intentionally waiting for the next ordinary hourly occurrence.

This rule exists to reduce missed-transition latency, not to increase background work volume. Typical self-wake-eligible cases include:
- PM published/read-backed a new executable Role CURRENT, Cursor/B2 PREPARED command, or other asynchronous lane dispatch and the downstream terminal result is still pending;
- PM dispatched a correction after `FIX_REQUIRED`, retry, or bounded control/scheduler recovery and the retried actor has not yet produced the expected state change;
- an automation was expected to run but its OUTBOX/Active control did not advance, and this PM run performed the governed re-wake/recovery action needed to try again;
- a terminal result is expected to unlock an immediately adjacent next lane and the producing actor is ACTIVE/recently released, so a short follow-up is materially more useful than an hour-later poll;
- PM repaired a PM-owned control whose downstream effect requires another actor to react before PM can safely finish the transition.

Self-wake is **not** triggered merely because some nonterminal state exists. Do not accelerate for pure `NEEDS_USER_INPUT`, explicit user hold/pause, external service/vendor approval, unavailable permission/credential owned outside PM, long-horizon watch whose `next-check-at` is later, or any other wait where a 5-10 minute PM rerun has no machine-observable chance to unlock work. An unchanged asynchronous wait from the previous PM run also does not by itself justify repeated short polling: another short self-wake requires fresh downstream progress, a new dispatch/retry/recovery action in the current run, or an existing retry/watch rule that explicitly makes another near-term attempt due. `QUEUE-RETRY-BUDGET-001`, `QUEUE-WATCH-POLL-001`, and stall/recovery rules bound repeated attempts.

Authorization/consent behavior for self-wake follows the common scheduler boundary in `QUEUE-SCHEDULE-INDEPENDENCE-001`; self-wake adds no separate authorization semantics.

Scheduler mechanics:
- fresh-read the PM automation immediately before any self-wake write; explicit `PAUSE_INTENT=USER_DIRECTED` always wins, and an unhealthy/stale PM scheduler is handled under `QUEUE-AUTOMATION-HEALTH-001` rather than masked by re-anchoring;
- if the PM automation is already due to run within the selected follow-up window, do not churn the schedule;
- compute the slot from a fresh current local clock. The normal short follow-up target is about **5 minutes** after the current PM run; use up to about **10 minutes** when a slightly longer downstream action is expected or to avoid colliding with another dollworld loop. Never publish a past/ambiguous just-fired DTSTART;
- re-anchor only the existing PM automation. Preserve prompt, title, timezone, enabled state, timing mode, and `RRULE:FREQ=HOURLY`; do not create a second one-off PM task. The re-anchored run becomes the next hourly recurrence anchor, so when no further short follow-up is justified the PM simply returns to one-hour cadence from its most recent run;
- verify the automation state after the update. Self-wake failure never invalidates the underlying dispatch/result/control state; the ordinary hourly recurrence remains the fallback and the exact scheduler retry condition is recorded when needed.

A short follow-up PM run still executes normal fresh-read/reconciliation and `QUEUE-PM-DRAIN-001`; it is not a special fast path that can skip authority checks. `QUEUE-RESULT-WAKE-001` and `QUEUE-CURSOR-RESULT-RELAY-001` may wake PM even earlier when a terminal result appears before the planned self-wake; whichever governed wake wins, duplicate schedule churn is suppressed by fresh-read/due-time checks.

## QUEUE-CONTRACT-001 — CURRENT / OUTBOX
CURRENT and stable OUTBOX are the only Role live-control state. Immutable packets, Activity entries, temp egress files, and detailed evidence are evidence/recovery inputs only; they never become a third queue state. Normal Role/PM polling therefore begins with CURRENT + stable OUTBOX and expands to evidence only when those two controls do not converge.

CURRENT minimum: state, assignment-key/generation, exact work, authority/predecessor, scope/forbidden scope, expected result, blocker/resume-condition when waiting. Optional same-Role forward authority is represented only by a `continuation-authority` block governed by `QUEUE-ROLE-CONTINUATION-001`; ordinary prose `next-work` is not execution authority. A non-terminal waiting state also carries `resume-watch`, a compact pointer to the control/artifact/user/external condition whose change can make the work executable again; use `USER` only when no internal or external machine-observable source can satisfy the condition. If the PM-issued work originated from an external PM request, the canonical CURRENT or Cursor Inbox must also carry `source-request-id: <request-id>` and `source-request-file-id: <Drive file id>` as provenance.
When an assignment participates in a PM fan-in/join that genuinely requires multiple terminal inputs before one downstream decision, CURRENT must carry a machine-readable join block: `fan-in-id`, `fan-in-authority`, and `fan-in-required-results` containing the exact required role/result identities or stable evidence pointers. Optional `fan-in-satisfied-results` may record already-consumed terminals. PM must re-evaluate the join block whenever authority, evidence identity, or the target decision changes; obsolete requirements are removed rather than waited on. Absence of a fan-in block means there is no cross-role join requirement to infer from prose.
OUTBOX minimum: matching key/generation, result/state, concise blocker/release token, evidence/output pointers, material resume condition and matching `resume-watch` if waiting.
Detailed evidence is referenced, not copied into control files. `source-request-id` / `source-request-file-id` are provenance only; they do not make the request itself execution authority.

## QUEUE-TRANSITION-001 — transitions
`READY` means executable work. `WAITING_UPSTREAM` means no executable portion remains **and an explicit watched dependency is useful to preserve on the Role lane**; it requires an exact resume condition plus `resume-watch`.

After a generation completes, the matching terminal OUTBOX consumes that CURRENT generation. If the consumed CURRENT carries an eligible `continuation-authority`, the owning Role may publish the exact N+1 successor under `QUEUE-ROLE-CONTINUATION-001`; otherwise PM performs a bounded same-role opportunity check against the terminal OUTBOX's explicit next steps, already-ready work in the current task family, applicable pending PM requests/sidework, and the next roadmap item when `CORE-ROADMAP-001` requires that read.
- If distinct safe Role-owned work exists, PM issues the next READY generation in the same run.
- If no such work exists, the lane may remain at the consumed terminal generation and rest. Do **not** mint a generation solely to transport `IDLE`, `TERMINAL_OK`, an already-proven decision, or “nothing to do”.
- Use a new `WAITING_UPSTREAM` generation only when there is a real blocked scope plus a machine-observable/user/external resume condition worth tracking on that lane. A user/external gate that blocks only one downstream subphase does not justify Role-level WAIT while non-dependent Role work remains executable.

A WAITING state is not permanent merely because its CURRENT generation is unchanged: when the watched source satisfies the resume condition, PM transitions/issues the now-executable work in the same run, or the owning Role proceeds with the already-authorized same generation under `QUEUE-ROLE-AUTONOMY-001` when no PM-owned mutation is needed. A consumed terminal CURRENT/OUTBOX pair, by contrast, needs no polling-specific reconciliation until new work or a relevant watched condition exists.

Do not mint a generation solely to transport an already-proven decision, normalize cosmetic state wording, or rerun completed work against unchanged evidence.

## QUEUE-RECONCILE-001 — generation reconciliation
If CURRENT is newer than OUTBOX, the owning Role must not silently exit merely because an older OUTBOX already exists.
- Executable CURRENT: before repeating substantive work after a prior interruption, check for a valid same-generation terminal result. Once one valid terminal result exists for the exact assignment-key/generation, substantive execution for that generation is consumed and MUST NOT run again; recovery is OUTBOX egress only. If multiple same-generation terminal evidence files exist, do not block merely because they are duplicated. Select deterministically: first prefer the terminal token required by CURRENT; among equivalent valid terminals use the earliest-created valid evidence as canonical recovery input and treat later equivalent copies as duplicate evidence. Only materially conflicting terminal verdicts/payloads for the same generation are an integrity blocker. If no valid same-generation terminal exists, perform substantive assigned work in that same Role run and write the matching generation result; a Role run MUST NOT end as `NO_ACTION`, status-only, scheduler-only, scoring-only, or relay-only after observing such an executable newer CURRENT. If the assignment cannot finish in that run, persist `WORKING` with material same-generation progress or the exact material blocker/progress and next bounded step before exit. Automation/scheduler invocation success by itself never satisfies this postcondition.
- Evidence creation for one generation is idempotent: use one deterministic generation/result identity and reuse an existing valid evidence artifact instead of creating another copy merely because stable OUTBOX is stale. A failed OUTBOX write never authorizes a substantive rerun.
- Non-executable CURRENT (`WAITING_UPSTREAM`, `SUPERSEDED`, or equivalent): before treating a machine-observable WAIT as non-executable, evaluate only its exact `resume-watch` under `QUEUE-WATCH-POLL-001` / `QUEUE-ROLE-AUTONOMY-001`. If the condition is satisfied and the same CURRENT fully defines the authorized work, execute that same generation instead of normalizing a stale wait. Otherwise normalize OUTBOX once to the matching generation/state with exact reason and resume condition; do not fabricate runtime work. `SUPERSEDED` never self-resumes.
An unexplained mismatch may trigger the bounded reconciliation reads permitted by CORE-READ-001.

## QUEUE-PARALLEL-FLOW-001 — dependency-DAG parallel dispatch / no role ping-pong
The Role split exists primarily to preserve parallel forward progress and clear responsibility boundaries. PM must schedule work by **actual dependency edges**, not by a habitual Role1 -> Role3 -> Role1 relay sequence. When two or more safe work items do not depend on one another and do not collide under `PARALLEL-COLLISION-001` / `PARALLEL-VERIFY-001`, PM issues them to their appropriate lanes in the same PM drain cycle instead of serializing them merely because they belong to the same Sprint, feature family, or evidence set. Parallel dispatch never means stacking multiple unconsumed executable generations onto one Role: each Role has at most one live executable CURRENT generation, and PM selects the highest-value safe item for that lane while other independent items remain candidates for later dispatch or other lanes.

Parallel dispatch is a bounded opportunity rule, not a utilization target. PM does not invent busywork merely to keep every Role occupied. **Resting, waiting, and `TERMINAL_CONSUMED` are nevertheless negative conclusions that require a bounded forward-work exhaustion proof; they are not the default after a Role finishes its current generation.** Before PM may end a run with a Role resting/waiting, it must check, in this order, the terminal OUTBOX explicit next steps, already-authorized work in the current task family, pending PM requests/sidework, collision-safe preflight/readiness/acceptance/evidence work, and the next accepted roadmap/Sprint workstream when the current lane facts do not already prove no such work can be executable. If any distinct safe Role-owned work is found, PM dispatches it in the same drain cycle. A dependency that blocks one downstream subphase does not prove the Role has no other forward work.

**Multi-idle guard.** When two or more Role lanes would otherwise be reported resting/waiting, or when all Role lanes would be non-active while the project/Sprint is not complete, PM must perform an explicit cross-role forward-work matrix before report. For each non-active Role, the matrix must establish one of: `(a)` a distinct READY generation was dispatched in this run; `(b)` the Role already has an unconsumed executable generation; or `(c)` no safe authorized work exists, with the exact limiting dependency/collision/authority fact. If PM cannot establish `(c)` from live controls and already-accepted authority, it must read the relevant Roadmap/next-work authority and continue searching rather than classify the lane as resting. A production single-writer collision on Cursor A does not, by itself, block Role1/2/3 read-only/preparation/acceptance work that does not touch the writer-owned tree.

A PM report with known safe authorized work left undispatched on an otherwise idle Role is invalid in that same run; there is no one-cycle or two-cycle grace period. Such a run is `PM_DRAIN_INCOMPLETE / FORWARD_WORK_NOT_DISPATCHED`, and the affected lane is not reported as successful rest. This is still bounded and non-speculative: PM may stop only after the exhaustion proof succeeds, and it must not invent semantics, duplicate acceptance, or violate `CORE-LANES-001`, `PARALLEL-COLLISION-001`, or `PARALLEL-VERIFY-001`.

Use **fan-out / fan-in** semantics for shared evidence:
- If multiple distinct judgements are genuinely required over the same immutable implementation/evidence state and neither judgement depends on the other's conclusion, dispatch those reviews in parallel. Each Role reads the same authoritative evidence directly and writes its own OUTBOX; PM performs the later gate/join.
- Do not make Role B wait for Role A's review merely so B can review the same unchanged facts, and do not return the same unchanged artifact to Role A after Role B unless a current authority explicitly requires a distinct second judgement or new evidence/delta invalidates the prior judgement.
- A downstream Role or PM may **consume** another Role's terminal evidence/result as an input when the receiving gate permits evidence reuse under `CORE-ACCEPT-001` / `AUDIT-EVIDENCE-001`. Consumption is not a mandatory full re-audit. If the receiving Role owns a distinct final decision, it performs only the minimum independent integration/delta check required for that decision; it must not mechanically repeat already-proven unaffected surfaces.

Same-item serial handoff is allowed only for a real dependency, for example: implementation must exist before acceptance; a failed audit creates a concrete fix that must complete before re-audit; one Role's output is itself the specified input/authority for another; or shared-resource/write collision forces serialization. The CURRENT/OUTBOX or task instruction must identify that dependency. `Role A finished, therefore send the same thing to Role B, then back to A` is not a dependency by itself.

PM should normally shape the active Role set as complementary workstreams consistent with `CORE-LANES-001`: Role1 on milestone acceptance/bounded preflight, Role2 on forward implementation readiness, and Role3 on trailing determinism/regression/FI/long-run verification. These are lane defaults, not a rigid Sprint-number assignment. A Role may work on a later preparation horizon while current production remains gated only when the work is **preparation-only**: read/analysis/decomposition/test-or-acceptance planning/evidence mapping or other reversible non-production preparation already authorized by current inputs. A closed Sprint transition gate forbids using this rule to start later-Sprint production implementation, mutate Git-tracked product code for that later Sprint, adopt a binding later-Sprint spec/product decision, or manufacture acceptance for work not yet authorized. `SPRINT-TRANSITION-001` / `CURSOR-SPRINT-ENTRY-001` remain hard boundaries.

Forward-preparation assignments are deliberately **bounded and preemptible at generation boundaries**. PM must not choose a large speculative preparation package that can monopolize a Role across repeated runs while higher-priority current-Sprint or critical-path work is ready. Preemption is state-sensitive and fail-closed:
- if the lower-priority assignment is still PM-owned `READY` and has not been claimed or materially started by the Role, PM may mark that generation `SUPERSEDED` with the higher-priority reason and then issue the next generation;
- if the Role has claimed the assignment or published same-generation `WORKING` / material progress, PM must not overwrite CURRENT mid-execution. It records the pending higher-priority need and waits for a safe persisted checkpoint or terminal result;
- once a safe checkpoint is persisted and the actor is no longer actively mutating that generation, PM may close/supersede the bounded preparation generation with explicit continuation evidence and dispatch the higher-priority generation;
- ambiguous claim/activity state is not permission to preempt. Resolve it under `QUEUE-WORKING-RECOVERY-001` / `QUEUE-DISPATCH-SAFETY-001` first.
If a preparation task needs multiple runs, it exposes same-generation material checkpoints under the normal WORKING contract; when a newer higher-priority authorized need arises, PM stops extending preparation solely for continuity and switches at the first safe generation boundary. This does not authorize overwriting another actor's active OUTBOX/CURRENT or unsafe mid-write interruption.

When a gate requires results from several lanes, the gate/task instruction identifies the exact **fan-in dependency set** (required result roles/keys or equivalent stable identities). PM joins only those required terminal results. A missing result blocks only that gate's dependency cone; other lanes continue under `QUEUE-BLOCKER-001`. PM must not convert a fan-in gate into project-wide serialization. Before continuing to wait on an incomplete fan-in, PM re-evaluates that required set when current authority, task identity, or superseding evidence changed. A result requirement that has been removed, superseded, or made unnecessary by current authority is deleted from the join condition and any now-obsolete queued Role work is reconciled/superseded under existing control rules; PM must not wait forever for an obsolete review. Conversely, a newly required independent judgement is added only from current authority, not inferred merely to keep a Role busy.

A gate-owned decision that normatively depends on completion of another step remains a real serial edge and is not parallelized away. In particular, Role1 Sprint transition certification under `SPRINT-TRANSITION-001` still starts only after the outgoing Sprint's required acceptance and `SPRINT-FINAL-001` completion evidence exist; parallel preparation or other Role reviews cannot substitute for or bypass that prerequisite.

## QUEUE-AUTONOMY-001 — generation vs auxiliary autonomous work
A distinct roadmap item or new binding deliverable requires PM-issued `NEW_WORK`; it is not silently promoted from idle time or same-boundary continuation.
Role-owned same-assignment continuation and bounded autonomous quality/preflight may run only inside the actor's lane and must remain auxiliary. PM-issued CURRENT/sidework always outranks fallback autonomous work.
A normal Role automation must not equate “no newer PM generation” with a mandatory no-op. Before idle exit, when CURRENT/OUTBOX are coherent and no PM-issued executable work exists, the Role may perform one bounded, non-duplicative auxiliary step only when a concrete unresolved item is already identified by the current task family, current OUTBOX/evidence, or an existing Role-owned readiness/verification checklist; the step must fit `CORE-LANES-001`, require no new product/spec authority, avoid production ownership outside the Role, avoid self-accepting work that requires independence, and avoid claiming a new binding task as complete. Examples include a bounded implementation-readiness delta, task-boundary preparation, or a non-binding verification/preflight artifact already implied by accepted/current inputs.
An explicit coherent `WAITING_UPSTREAM` CURRENT is not an auxiliary-work trigger: by `QUEUE-TRANSITION-001` it asserts that the bounded same-role opportunity check found no safe Role-owned work. A Role automation therefore does not override a valid Role-level WAIT with auxiliary work. Auxiliary fallback is available only after a consumed/terminal assignment or otherwise coherent non-waiting idle boundary, and stops immediately when PM publishes a newer command.
Do not invent new roadmap scope, create repeated “keep busy” artifacts, reread broad history/roadmap merely to find work, or redo a terminal generation. If no concrete non-duplicative auxiliary step is already available, idle exit is correct. Auxiliary work uses a separate artifact/evidence pointer when useful and does not overwrite a terminal main OUTBOX result unless the true assignment state materially changes.


## QUEUE-EXTERNAL-REQUEST-001 — external dollworld thread -> PM intake
When the user gives a dollworld thread other than the designated active PM/control runtime a request that would create, redirect, reprioritize, pause, cancel, or otherwise materially change a distinct work item, that thread must submit a PM request instead of directly writing `ROLE*_CURRENT.md`, `CURSOR_INBOX.md`, or `CURSOR_B2_INBOX.md`.

Physical request placement and inbox/processed lifecycle locations are owned by `ARTIFACT-PM-REQUEST-001`; this rule owns intake, precedence, reconciliation, and dispatch semantics only. The submitting thread writes one request once and then treats it as PM-owned; corrections create a superseding request rather than competing edits. A request is not authority, reservation, dispatch, acceptance, or permission to begin work. Existing live CURRENT/OUTBOX/Inbox/Active controls remain authoritative until PM dispatch changes them.

Request minimum:
- `request-id` and `created-at`;
- `source-thread` and `requested-by` (`USER` when user-directed);
- concise `intent` / requested outcome;
- `requested-mode` such as `MAINLINE_CANDIDATE`, `AUXILIARY_WHEN_FREE`, `CORRECTION`, or `HALT_OR_CANCEL`;
- for `HALT_OR_CANCEL`, preserve the user's requested stop boundary (`IMMEDIATE`, `WHEN_SAFE`, `AFTER_CURRENT_STEP`, or an equally explicit boundary) rather than weakening it to advisory priority;
- relevant authority/artifact pointers;
- forbidden scope / collision constraints when known;
- user review/approval gate when the request must stop before a later phase;
- optional `suggested-lane`; lane choice is non-binding and PM-owned;
- optional `supersedes` request-id;
- when the request becomes `DEFERRED` or `NEEDS_USER_INPUT`, PM adds `resume-watch` together with the exact resume condition; the immutable submitter section need not predict it.

Request identity / collision safety:
- Normal creation requires `request-id` to be unique across both non-terminal and processed PM-request storage. Before upload, the submitting thread performs a bounded exact-ID check. If the ID already exists, it must not overwrite, reuse, or edit the existing request; mint a new ID and upload a new raw Markdown request.
- Drive file ID is the stable physical identity for a submitted request. PM records/uses the pair `(request-id, Drive file id)` when resolving or dispatching. A dispatched canonical CURRENT/Inbox therefore carries both `source-request-id` and `source-request-file-id`.
- If a race or legacy artifact produces two files with the same `request-id`, PM must not guess identity from filename or request-id alone. Equivalent immutable request facts may be collapsed by marking the later file `DUPLICATE`; materially different colliding files remain distinct by Drive file ID and are processed separately only with the full identity pair.
- A `supersedes` reference that is ambiguous because multiple files share the target request-id must also identify the intended target Drive file ID (for example in the new request context). Without an unambiguous target, do not alter or cancel either candidate; resolve the new request as `NEEDS_USER_INPUT` with the exact identity question.

Legacy request compatibility:
- Requests submitted before this contract used `status: PENDING` instead of `submission-state: SUBMITTED` and may omit newer template fields. Treat such a raw request as a valid submitted legacy request when its immutable intent/context and `PM resolution` section are otherwise readable.
- Do not rewrite immutable legacy request facts merely to normalize the template. Apply current `QUEUE-EXTERNAL-REQUEST-001` semantics at processing time, add only PM-owned resolution/provenance fields as needed, and preserve the original submission text for history.

User stop/cancel precedence:
- An explicit user instruction to stop or cancel revokes authority for further substantive continuation of the targeted work. PM must prevent new substantive work and stop already-running work at the user's stated boundary; for `IMMEDIATE`, use the earliest safe/atomic boundary.
- PM may choose only the safe stop mechanics, reconciliation, and cleanup necessary to leave controls/evidence coherent. PM may not convert an explicit stop/cancel into ordinary `DEFERRED` work merely because continuing would be convenient.
- If the user explicitly says to finish the current step or stop when safe, that boundary is binding instead of `IMMEDIATE`.

Superseding-request reconciliation:
1. resolve the request named by `supersedes` before dispatching the replacement;
2. if the superseded request is still `PENDING`, `DEFERRED`, or `NEEDS_USER_INPUT`, mark its PM resolution `SUPERSEDED`, set `superseded-by`, and move it to processed storage under `ARTIFACT-PM-REQUEST-001`;
3. if the superseded request was already `DISPATCHED`, follow its `dispatch-pointer` / `source-request-id` + `source-request-file-id` to the canonical lane control. If the command has not begun, replace or neutralize it before new dispatch; if it is ACTIVE/WORKING, issue the minimum correction/halt/rework through that same lane instead of starting a duplicate task; if it already completed, preserve the completed history and treat the new request as a correction/follow-up rather than retroactively erasing it;
4. record the prior dispatch pointer and reconciliation outcome in the new request's PM resolution. A superseding request never creates two simultaneously authoritative commands for the same intended work.

Request arbitration / idempotency:
- PM enumerates the relevant non-terminal request set before committing conflicting dispatches. Provider listing order, filename order, or search ranking is not priority. Explicit user correction/stop/cancel and supersession are reconciled first; otherwise roadmap/dependency/lane constraints determine safe order. Do not create two simultaneously authoritative commands for one lane merely because two requests were discovered in the same run.
- Before dispatching a `PENDING` request, check the target canonical lane controls for the exact `(source-request-id, source-request-file-id)`. If a matching command already exists from a prior interrupted PM run, reconcile that command and finish the request lifecycle; do not mint or dispatch the same work again. If a terminal request resolution remains physically in inbox because only the lifecycle move failed, treat it as a partial lifecycle transition: retry/reconcile the move and do not redispatch.

PM processing:
1. reconcile the request against `PROJECT_ROADMAP.md` when `CORE-ROADMAP-001` requires it and against freshly read current lane/lock state as required by `QUEUE-DISPATCH-SAFETY-001`;
2. preserve explicit user priority/correction/stop/cancel meaning; except for binding user stop/cancel semantics above, PM chooses the safe lane, dispatch timing, and preemption decision;
3. resolve the request as `DISPATCHED`, `DEFERRED`, `REJECTED`, `DUPLICATE`, `NEEDS_USER_INPUT`, or `SUPERSEDED`;
4. for `DISPATCHED`, issue the normal canonical CURRENT/Inbox `NEW_WORK`, include both `source-request-id: <request-id>` and `source-request-file-id: <Drive file id>` on that canonical command, and record its dispatch pointer in the request;
5. `DEFERRED` and `NEEDS_USER_INPUT` are non-terminal and remain in inbox. Both require an exact `resume-condition` and `resume-watch`; `NEEDS_USER_INPUT` also records the exact user question/input needed. They are re-evaluated under `QUEUE-FAST-001` and must not become orphaned merely because the request file itself did not change. `DISPATCHED`, `REJECTED`, `DUPLICATE`, and `SUPERSEDED` are terminal request-processing dispositions and move to processed storage under `ARTIFACT-PM-REQUEST-001`;
6. PM may append/update only the `PM resolution` section after submission; the original request facts remain intact;
7. `DISPATCHED` is committed only after the canonical CURRENT/Inbox command and any required canonical instruction have been written and read back with matching task/request provenance. Do not move a request to processed or publish a terminal dispatch result first. If command publication or the lifecycle move fails, preserve the request as non-terminal and reconcile the partial state on the next authorized run under `QUEUE-TRANSIENT-FAILURE-001` / `QUEUE-CONTROL-RECOVERY-001`.

A source thread may prepare proposal/reference artifacts that are inside its own role and explicitly requested by the user, but those artifacts do not self-dispatch implementation or consume a Role/Cursor lane. If the same runtime is actually the designated active PM/control runtime, it may dispatch directly only after performing the normal PM live-control reads and matching both executor class and `executor-instance` under `QUEUE-PM-EXECUTOR-001`; `CHATGPT_THREAD` never means “any ChatGPT conversation”.

## QUEUE-BLOCKER-001 — blocker record
A material blocker record has: owner (`PM|ROLE1|ROLE2|ROLE3|CURSOR|USER|EXTERNAL`), minimum resolution action, resolution state, exact resume condition, and the affected task/lane/dependency scope. Internal safe resolution is executed/assigned in the same PM run. User escalation is only for genuinely missing user authority/input.
A blocker is scoped to its actual dependency cone. A user gate, external dependency, or stopped task in one item/lane must not freeze unrelated safe roadmap work or other lanes. The same rule applies inside one Role lane: a gate such as `do not generate more images until user approval` blocks that protected production step, not unrelated QA coordination, implementation-readiness, task-boundary preparation, or other independently authorized Role work. Role-level WAIT is valid only when the gate/dependency actually covers all safe work currently available to that Role or no such work exists after the bounded opportunity check in `QUEUE-TRANSITION-001`. PM keeps only the blocked dependency non-executable and continues independent executable work when authority and collision rules permit.

## QUEUE-USER-DECISION-PREFLIGHT-001 — canonical authority check before user-decision wait
Role1 / Role2 / Role3 MUST NOT directly classify a blocker as `owner: USER`, `WAITING_USER_DECISION`, or `NEEDS_USER_INPUT`, and MUST NOT directly ask the user to choose product semantics. A Role may only emit `CANDIDATE_USER_DECISION` together with the evidence contract below. Only the active PM/control runtime may promote a validated semantic candidate to an actual USER-owned blocker or user question.

This gate is semantic, not label-based. Any request for user input whose answer would choose, change, clarify, or authorize product/gameplay semantics is a `USER_DECISION` escalation regardless of the state label, owner label, prose location, queue type, or whether it originated from a Role, PM, failover PM, readiness packet, audit finding, automation run, or direct PM observation. Renaming the state to `BLOCKED`, `WAITING_UPSTREAM`, `PM_DECISION`, `QUESTION`, `CONFIRMATION`, or equivalent does not bypass this rule.

PM-originated semantic questions are not exempt. If PM itself discovers a possible semantic ambiguity without a Role candidate, PM MUST first materialize an equivalent `CANDIDATE_USER_DECISION` evidence record and independently validate it in the same run before asking the user. No product-semantic question may be surfaced directly from PM scratch reasoning, chat memory, a readiness summary, or a single search result.

Before PM may promote a candidate to `owner: USER`, or before any Role may emit `CANDIDATE_USER_DECISION`, it MUST perform a bounded authority preflight against the current accepted specification sources relevant to that decision. At minimum this means searching the canonical `SPEC.md`, the relevant accepted mini-spec/freeze when one exists, `SPEC_CHANGELOG.md` or equivalent accepted change history, and already-recorded explicit user decisions whose scope matches the question. Source selection/currentness MUST be reconciled using `SPEC-AUTH-001` and `SPEC-STATUS-001`; an arbitrary Drive mirror, duplicate filename, stale copy, proposal, readiness note, or historical snapshot is not sufficient merely because its text is convenient. A draft/proposal/preparation artifact is comparison input only and MUST NOT create a new user decision merely because its candidate value is more specific than the accepted authority.

Every `CANDIDATE_USER_DECISION` record MUST include all of the following fields:
- `spec-authority-read`: exact canonical SPEC path/ID actually read or searched;
- `spec-authority-status`: how that source was established as current accepted authority under `SPEC-AUTH-001` / `SPEC-STATUS-001`, including version/freeze/status identity when applicable;
- `spec-section`: exact section/heading or bounded search terms that were checked;
- `spec-result`: exactly one of `RESOLVED | PARTIAL | CONTRADICTORY | NOT_SPECIFIED`;
- `spec-changelog-read`: exact accepted changelog/history source checked;
- `spec-changelog-search`: exact bounded terms/section used for the decision;
- `accepted-user-decisions-read`: exact prior accepted user-decision/history source(s) checked, or `NONE_FOUND_AFTER_SEARCH`;
- `accepted-user-decisions-search`: exact bounded search scope/terms used; this is mandatory even when the result is `NONE_FOUND_AFTER_SEARCH`;
- `existing-authority-result`: concise statement of what current authority already determines;
- `remaining-question`: smallest remaining product-visible question, if any;
- `why-spec-does-not-answer`: why current accepted authority does not fully determine that remaining question.

A field is not satisfied by a bare filename/ID, `checked`, `searched`, `none`, or equivalent assertion when the field requires status, section, terms, scope, or result. Evidence must be specific enough for PM to reproduce the bounded lookup without relying on the originating actor's memory.

Missing or non-reproducible required evidence makes the candidate invalid. PM MUST classify it as `INVALID_USER_BLOCKER / PREFLIGHT_EVIDENCE_MISSING`, MUST NOT ask the user, and MUST return the item to the originating lane for authority search/reconciliation while continuing independent executable work.

The preflight resolves the candidate question as follows:
1. If `spec-result: RESOLVED`, PM MUST classify the candidate as `INVALID_USER_BLOCKER / ANSWER_EXISTS_IN_AUTHORITY`, bind the accepted answer, and resume/continue the work without user escalation.
2. If accepted authority constrains only part of the behavior (`PARTIAL`), preserve the resolved part and allow escalation only for the smallest genuinely unresolved product-visible delta.
3. If `CONTRADICTORY`, PM MUST first reconcile precedence/currentness using canonical SPEC status/change-history rules; contradiction is not itself permission to ask the user unless current accepted authority remains genuinely ambiguous after that reconciliation.
4. If `NOT_SPECIFIED`, PM MUST verify the accepted changelog/history and prior explicit user decisions before promotion. Absence from one file is not proof of missing authority.
5. If the remaining difference is an internal implementation/canonicalization detail that can be derived deterministically without changing player-visible semantics, resolve it internally under the applicable technical authority instead of escalating it.
6. Only if multiple materially different product-visible outcomes still remain after the bounded search may PM promote the candidate to `owner: USER`; the final blocker/question MUST carry the validated evidence fields and the exact unresolved alternatives.
7. A preparation/readiness document labeling an item unresolved is never sufficient evidence for USER ownership. The current canonical specification/history must be checked directly.
8. PM MUST preserve the validated evidence in the durable blocker/request/control record that causes the wait. Ephemeral chat reasoning alone is insufficient to keep a lane in USER wait.
9. After a semantic candidate is validly promoted to `owner: USER`, PM MUST surface the exact smallest validated question in the designated active ChatGPT PM thread. A Role thread, Cursor artifact, Drive queue, scheduled-run log, or background control record does not by itself count as user notification. If the current PM runtime cannot post into the designated active PM thread, persist `USER_NOTIFICATION_PENDING` with the blocker/request identity and do not claim the user was asked; retry notification at the next active-thread opportunity while independent work continues.
10. A user response obtained in another dollworld thread is valid input only after it is routed back to PM using the governed response/request path (`QUEUE-WATCH-POLL-001` / `QUEUE-EXTERNAL-REQUEST-001`) or is directly observed by the active PM runtime. Do not leave the originating semantic wait unresolved merely because the answer arrived outside the PM thread.

**Hard promotion gate.** Until the above preflight reaches a valid promotable USER decision, no actor may persist or continue `owner: USER`, `WAITING_USER_DECISION`, `NEEDS_USER_INPUT`, an OPEN confirmation-queue item, or a user-facing semantic question for that candidate. This prohibition applies even when the item was already written by an older run. Discovery of such a prematurely promoted state is a reconciliation defect: invalidate/withdraw the USER wait, repair the affected live control or queue disposition, and continue/reroute work under current accepted authority. `QUEUE-USER-CONFIRMATION-001` owns the durable confirmation-queue surface; this rule owns the authority test that must pass before that surface may be OPEN.

PM validation is independent of the Role's label. `owner: USER` written by a Role without PM promotion is mechanically invalid and MUST be treated as `CANDIDATE_USER_DECISION` at most; it cannot stop the lane or be surfaced to the user. This applies equally to Role-authored OUTBOX, readiness packets, audit findings, and failover-PM observations.

Legacy or already-existing USER waits are not grandfathered. Before PM surfaces, repeats, or continues an existing `owner: USER`, `WAITING_USER_DECISION`, `NEEDS_USER_INPUT`, or equivalent semantic wait, PM MUST validate it against this current evidence contract. If the evidence is missing, stale, non-current, or the answer now exists in accepted authority, PM invalidates/downgrades the USER wait and resumes or reroutes work as applicable. A previously asked but unanswered question does not remain valid solely because it was asked before this rule revision.

Operational user input that does not choose product semantics—such as an explicitly required credential/permission, an ambiguous external resource identity, or an explicit user-directed pause/resume choice—may use `NEEDS_USER_INPUT` without being converted into `CANDIDATE_USER_DECISION`. The blocker must state why the input is operational rather than semantic. If resolving the input would choose gameplay/product behavior, this semantic gate applies instead.

This preflight is intentionally bounded: search the relevant canonical authority by the decision's concrete terms and nearby synonyms; do not reread the entire specification corpus when a targeted lookup can establish the answer. It does not permit changing accepted specification semantics without user/spec authority; it prevents duplicate or unnecessary user questions.

## QUEUE-BLOCKER-ROUTE-001 — blocker routing before actor exit
A blocker is an item/lane condition, not automatic authority to end the current run. Every active PM / Role1 / Role2 / Role3 run that observes a material `BLOCKED` / non-executable condition must first record the exact blocker and then perform a bounded continuation pass for other safe executable work already authorized to that actor. The actor may end normally only after that pass proves there is no independent safe work it can still advance in the same run and no existing recovery/routing path it owns can be applied. A blocker on one lane/item must not freeze unrelated lanes/items. Do not invent speculative work merely to avoid a blocker.

For Role1 / Role2 / Role3, after recording the exact blocker on the current assignment, continue any deterministic continuation or other already-authorized independent work available under `QUEUE-ROLE-AUTONOMY-001` / `QUEUE-ROLE-CONTINUATION-001`; if none exists, exit with the exact blocker/resume condition while keeping the scheduler enabled. `BLOCKED`, `WAITING_UPSTREAM`, `NEEDS_USER_INPUT`, or equivalent state is never by itself permission to disable the Role automation.

Every active PM run, regardless of whether it was triggered by user `k` / `ｋ`, another user message, or the scheduled PM automation, must classify every newly observed material `BLOCKED` / non-executable condition before the run may report waiting or end. The classification is:
- **WORK_IMPOSSIBLE_OR_AUTHORITY_BLOCKED**: the work itself cannot currently be performed because required authority/input/external state is genuinely unavailable to every authorized lane; or
- **EXECUTOR_CAPABILITY_BLOCKED**: the assigned actor cannot perform the required operation with its execution surface/tooling, but the work itself remains executable by another authorized lane.

For `EXECUTOR_CAPABILITY_BLOCKED`, PM must perform a bounded same-run capability-routing pass before reporting the blocker. Using current lane authority, `QUEUE-CAPABILITY-DISCOVERY-001`, `CORE-LANES-001`, `PARALLEL-COLLISION-001`, and applicable Cursor/Role publication rules, PM checks whether another existing lane can perform the missing operation without violating acceptance independence, writer ownership, worktree/index collision, or current Active locks. If one safe capable lane is uniquely available, PM dispatches the narrowest required helper/evidence/recovery task to that lane in the same PM run and read-backs the canonical command before exit. Do not wait for a user nudge merely because the originally assigned actor lacks that capability.

A capability-routable blocker is not a valid terminal PM wait. PM must not end the run with only `BLOCKED`, `WAITING_UPSTREAM`, `NEEDS_USER_INPUT`, or equivalent narration when a safe authorized helper dispatch is already uniquely determined. The originating Role may remain non-executable while the helper runs, but its resume condition/resume-watch must point to the routed helper result rather than to the user. If the capable lane is presently ACTIVE on conflicting work, publication would violate collision/authority rules, or more than one materially different routing choice exists, record that exact remaining routing constraint instead of pretending the underlying work is impossible.

The helper lane does not inherit the blocked Role's acceptance authority. Local/runtime evidence collection, file inspection, browser/localhost interaction, repository reads, or other execution-surface work may be delegated; the owning Role still performs any independent readiness/audit/verdict step required by its authority after the helper result returns. This rule routes capability, not decision authority.

Example: when Role2 is blocked only because its ChatGPT execution surface cannot read an exact local ZIP/package and an idle collision-safe Cursor A lane can read that local artifact, PM dispatches the exact local artifact inspection/recovery helper to Cursor A in the same run; PM does not report Role2 as simply waiting on an unavailable capability.

## QUEUE-PROVISIONAL-SOURCE-001 — provisional source / authority split
A source artifact may be usable for **non-destructive analysis and preparation** even when its canonical-authority status is not yet proven. PM and Roles must classify these as two separate questions instead of collapsing them into one blocker:
- **SOURCE_USABLE_FOR_ANALYSIS**: the bytes/content are accessible enough to inspect, expand, compare, extract, map deltas, identify contradictions/obsolete terminology, prepare implementation-readiness notes, or cut candidate next work without mutating canonical product/spec authority; and
- **SOURCE_CANONICALITY_CONFIRMED**: the artifact is proven to be the authoritative source/version for adopting normative semantics, replacing canonical spec, accepting an implementation against that exact source, or making other authority-sensitive irreversible/binding decisions.

A hash mismatch, missing expected hash, filename/version-label uncertainty, provenance uncertainty, or lack of final canonical adoption proves only that `SOURCE_CANONICALITY_CONFIRMED` is false unless it also makes the bytes/content unreadable or materially ambiguous for the intended analysis. It does **not** by itself make the whole assignment non-executable. When the artifact is accessible, the actor continues every safe non-destructive step that does not require canonical adoption and records the canonicality question separately.

For provisional packages/drafts, allowed continuation normally includes: expand/read the package; inventory contents; compare against accepted Sprint/spec/history artifacts; identify contradictions, omissions, stale names/terms, schema/API deltas, and implementation implications; prepare design/readiness material; isolate work that is executable under already-current authority; and separate only the decisions that genuinely require user/PM/spec authority. Do not represent provisional conclusions as adopted canonical semantics, do not overwrite the canonical spec/source solely from the provisional artifact, and do not grant acceptance based only on unconfirmed provenance.

PM/Role must not leave a lane in `WAITING_UPSTREAM`, `BLOCKED`, `NEEDS_USER_INPUT`, or equivalent solely because canonicality/hash confirmation is pending while safe analysis/preparation remains executable. Before such a wait is valid, apply `QUEUE-TRANSITION-001` and `QUEUE-BLOCKER-001` to prove that no independent non-destructive continuation remains. If exact bytes are inaccessible/unreadable, or a disputed identity changes the meaning of the analysis itself so that more than one materially different interpretation remains, record that narrower blocker.

Example: an accessible `v0.2.2-draft.zip` whose hash does not match an expected canonical hash may still be used as the **working analysis base** for extraction, spec-delta review, contradiction/obsolete-term discovery, and Sprint2 readiness decomposition. Only the separate question “may this exact package be adopted as the canonical v0.2.2 authority?” remains gated on canonicality confirmation.

Do not reread the full corpus and do not repeat an unchanged preflight. Classification follows CORE-BLOCK-001.

## QUEUE-PM-EXECUTOR-001 — switchable PM executor
`audit/assignments/PM_EXECUTOR.md` is the fixed live selector for which runtime may exercise the PM control lane. Its `active-executor` is one of `CHATGPT_THREAD` or `CURSOR`; `executor-instance` is a non-empty logical runtime identity; `epoch` increases whenever either the executor class or designated instance changes. `CHATGPT_THREAD` means the designated PM/control ChatGPT runtime, not every ChatGPT thread in the dollworld project.
Only a runtime whose executor class **and** declared runtime identity both match `active-executor` + `executor-instance` may perform PM-owned control writes such as Role CURRENT issuance, Cursor Inbox issuance, PM-side reconciliation, or assignment-loop configuration changes. A runtime that matches only `CHATGPT_THREAD`/`CURSOR` but not the instance is inactive and may inspect state but must not compete for those writes.
`CURSOR` in this selector means a Cursor-hosted PM/control runtime. It is not Cursor A or Cursor B2 implementation-lane identity by itself and does not acquire or bypass `CURSOR_ACTIVE_TASK.md` / `CURSOR_B2_ACTIVE_TASK.md`. If the same Cursor environment later performs implementation work, that work separately follows the applicable `CURSOR-*` rules.
A switch changes the executor only: existing Role CURRENT/OUTBOX, Cursor Inbox/Active, accepted evidence, roadmap, and Git/spec authority remain in force and are not reset or recreated. A handoff from one ChatGPT PM thread/runtime to another while `active-executor` remains `CHATGPT_THREAD` still changes `executor-instance` and increments `epoch`. Before the first PM action after an epoch change, the newly active executor re-reads the compact live controls under `QUEUE-FAST-001` and reconciles any already-consumed state under `CORE-STATE-001`.
Every PM automation/run checks all three selector fields (`active-executor`, `executor-instance`, `epoch`) before PM-owned writes; a previously active thread/runtime does not retain write authority merely because its prompt or handoff is older than the current epoch.
For the canonical PM assignment-loop automation, its own fixed logical runtime identity is stable actor/scheduler metadata and MUST be declared in the non-normative automation shell (for example `ExecutorInstance=<fixed PM automation runtime identity>`). This shell value identifies that automation runtime; it is not the live selector, is not copied from the current epoch, and grants no PM authority by itself. Each run still fresh-reads `PM_EXECUTOR.md` and may perform PM-owned writes only when the shell-declared instance matches the selector's current `executor-instance` and the current executor class/epoch fencing passes. Failover changes the selector rather than rewriting this fixed automation identity; on selector mismatch the automation remains enabled but performs no PM-owned writes.
If the selector is missing, malformed, lacks `executor-instance`, or names an unsupported executor/instance, do not guess ownership or perform ordinary PM writes. A mechanically malformed/partially-written selector with the same stable Drive ID may be repaired only under `QUEUE-CONTROL-RECOVERY-001`; this selector-only recovery does not authorize task dispatch and does not increment `epoch` unless the executor designation itself intentionally changes.

## QUEUE-PM-SCORE-RECOVERY-001 — PM self-recovery from Role-authored score evidence
The active PM executor uses Role-authored `PM_SCORE` as bounded external control-quality feedback, never as authority and never as a target metric to optimize directly. At the start of each PM run, after validating `PM_EXECUTOR` but before ordinary `QUEUE-PM-DRAIN-001`, PM reads at most the latest `PM_SCORE` entry from each of Role1 / Role2 / Role3 in the fixed Activity stream. PM must not author, edit, resolve, delete, suppress, or rewrite those Role-authored entries.

A latest Role score triggers targeted score recovery when **either** (a) total score is `<50/100`, **or** (b) `drain <=10`, **or** (c) `recovery <=10`. Dimension-triggered recovery exists because a material drain/recovery defect can be masked by stronger dispatch/autonomy totals. `dispatch` or `parallelism` deductions alone do not trigger score-driven mutation; they remain diagnostic unless another governing rule independently requires action. Missing-evidence-only deductions do not by themselves force a mutation.

For every triggered Role score, PM MUST parse that entry's observable `reason` / `blocker`, fresh-read only the directly implicated live controls, and classify each allegation as `CONFIRMED`, `STALE/ALREADY_RESOLVED`, or `UNSUPPORTED_BY_FRESH_STATE`. A confirmed PM-owned defect becomes a mandatory recovery action in the current run; PM may not finish with a normal idle/wait/report while that safe recovery action remains executable. If the same confirmed PM-owned stop reason survives the current recovery attempt and is still present at the next PM observation, PM must treat it as a `QUEUE-STALL-RECOVERY-001` control defect rather than merely reporting the unchanged wait again.

If two or more distinct Roles trigger score recovery in the same PM run and their reasons point to still-fresh PM-owned defects, PM enters `SCORE_DRIVEN_RECOVERY` before ordinary drain reporting: repair all confirmed safe defects, then execute normal `QUEUE-PM-DRAIN-001` to fixed point, read back affected controls, and only then proceed to `QUEUE-REPORT-001`. Score-driven recovery does not weaken any user-decision, Git, acceptance, collision, monotonicity, or executor fences.

PM never performs work merely to raise its score. Recovery success is established from live control closure; the score can improve only when a later Role independently observes better behavior and appends a new score. A PM run that sees a triggered score and leaves a confirmed safe PM-owned defect unrepaired is `PM_DRAIN_INCOMPLETE / PM_SCORE_RECOVERY_MISSED`, not a normal idle/wait result.

## QUEUE-ROLE-AUTONOMY-001 — Role-side autonomous convergence for already-authorized transitions
Role1 / Role2 / Role3 are independent execution lanes, not passive workers that require PM to relay every already-determined state transition. The PM remains the coordinator for priority, cross-lane conflict resolution, genuinely new assignment choice, and any transition that still requires authority judgment. It is **not** a mandatory relay for a transition whose exact next action is already mechanically determined by the Role's own live control/result and current normative rules.

Every Role run performs this bounded convergence check after resolving its logical CURRENT/OUTBOX state under `QUEUE-CONTROL-RECOVERY-001` and before ordinary `NO_ACTION` exit:
1. **Satisfied local watch.** If the Role's CURRENT is `WAITING`, `WAITING_UPSTREAM`, or equivalent and its `resume-watch` is machine-observable, the Role reads only the exact watched source needed to evaluate the condition. When the condition is satisfied and the same unconsumed CURRENT body already fully defines the authorized work, the Role proceeds with that same generation immediately. It does not wait for PM to rewrite the state label to `READY`. A stale waiting label is transport metadata, not execution authority. The Role writes normal progress/terminal evidence to its own OUTBOX/recovery path.
2. **Local result egress recovery.** If the Role completed substantive work and its canonical OUTBOX write failed, but a valid same-generation governed recovery checkpoint or `TMP_ROLE<role>_G<generation>_OUTBOX_EGRESS` proves the exact terminal payload, the Role first attempts its own canonical OUTBOX convergence under `QUEUE-CONTROL-RECOVERY-001`. It must not wait for PM merely to copy an already-final Role-owned result into the stable OUTBOX.
3. **Deterministic continuation after terminal consumption.** If the Role's own generation is terminal-consumed and the consumed CURRENT already contains a valid pre-authorized `continuation-authority` for one **distinct, exact, safe next assignment for the same Role**, the Role must not remain `NO_ACTION` waiting for PM. It applies `QUEUE-ROLE-CONTINUATION-001`. A terminal OUTBOX `next-work` statement, a vague suggestion such as `continue Sprint3`, a roadmap phase name alone, or a need to choose among multiple valid tasks is not continuation authority and remains PM work.

**Safety boundary.** This rule does not permit a Role to invent gameplay semantics, self-approve an acceptance verdict that requires independent authority, bypass Git/spec/audit fences, override another Role/Cursor-owned active task, choose among multiple competing next tasks, or convert a genuine user/external wait into internal work. Those remain PM/authority decisions. It also does not require a transport-only generation when no distinct safe work exists; a genuinely exhausted terminal lane may rest.

**Failure semantics.** If a Role proves that deterministic continuation is required but cannot complete `QUEUE-ROLE-CONTINUATION-001` because its own control/provider path is unavailable, it records the exact continuation blocker/retry condition and retries on a later Role run. It may not report ordinary `NO_ACTION` or healthy idle while the same already-authorized continuation remains undispatched. Other Roles continue independently under `QUEUE-LOCAL-ISOLATION-001`.

This rule makes distributed execution fail-open for **already-authorized forward progress**: loss or delay of one PM run may increase coordination latency, but must not by itself stop a Role whose next action is already determined.

## QUEUE-ROLE-CONTINUATION-001 — narrow same-Role deterministic continuation publication
This rule is the only exception that allows Role1 / Role2 / Role3 to publish a new generation into its **own** `ROLE*_CURRENT.md` without becoming the PM executor. It is a capability carried forward by the already-issued CURRENT, not a PM failover lease. It never changes `PM_EXECUTOR.md`, never enters `SURROGATE_PM`, never uses failover candidate priority, and never grants authority over another Role, Cursor lane, PM request, Roadmap, spec, acceptance verdict, or automation configuration.

**Pre-authorization / provenance gate.** Self-publication is permitted only when the terminal-consumed CURRENT for generation N already contained a `continuation-authority` block before the Role produced its terminal result. That block must pin either (a) the complete next command contract, or (b) a stable canonical command-template pointer plus immutable revision/hash that resolves to one complete next command contract. At minimum the authorized successor resolves to: exact `next-assignment-key`, exact bounded work, authority/predecessor pointers, scope/forbidden scope, expected result, any required source-request provenance, and an explicit `continue-on-terminal` predicate over generation N. `continue-on-terminal` must name the exact predecessor terminal result/value set that permits continuation; omission is invalid. A normal success-only chain names only the exact successful terminal result. `BLOCKED`, `FIX_REQUIRED`, cancellation, supersession, or any other terminal not explicitly listed fails closed to PM coordination and must not advance merely because N is technically terminal. The block also carries `mode: SAME_ROLE_EXACT` and may contain `valid-through-generation: N+1`; absence or ambiguity fails closed to PM coordination. A Role-authored OUTBOX/result/evidence may repeat or recommend a successor but can never create, broaden, or replace `continuation-authority`.

When PM issues a CURRENT and current authority already determines one safe same-Role successor with a complete command contract, PM MUST include this bounded `continuation-authority` so one missed PM run cannot stop the lane. PM MUST omit it when the successor depends on the current result's substance, a future user/product/spec choice, independent acceptance outcome, cross-lane scheduling choice, or any other information not already fixed at issuance time.

**Deterministic identity.** The autonomous successor for consumed generation N is always generation N+1 and carries `issued-via: ROLE_CONTINUATION`, `previous-assignment-generation: N`, the pinned `continuation-authority` identity, and a deterministic `continuation-id` derived from `(role, N, authority identity/revision, next-assignment-key)`. Any PM or Role writer issuing that same authorized N+1 successor must use the same continuation identity and materially identical command contract. A terminal OUTBOX alone is never an input to the continuation-id except as proof that N is consumed.

**Publication fence.** Before writing, the Role resolves the newest valid logical generation under `QUEUE-CONTROL-RECOVERY-001`, fresh-reads its stable CURRENT and OUTBOX, and applies `QUEUE-DISPATCH-SAFETY-001` / `CORE-MONOTONIC-001`. It must first prove that the canonical or governed-recovery terminal payload for N satisfies the pinned `continue-on-terminal` predicate exactly. A different terminal class/value makes the continuation ineligible and returns the lane to PM coordination without publishing N+1. It may write only when N is still the newest logical consumed generation and no valid N+1 command exists. If N+1 already exists with the same `continuation-id` and equivalent contract, the Role adopts/executes that command instead of writing. If N+1 exists with a different identity/contract, or any unresolved same-generation overlay/conflict exists, the Role does not overwrite it; classify `CONTINUATION_COLLISION` and route bounded reconciliation to PM.

Immediately before the write, the Role rechecks its stable CURRENT/OUTBOX pair and revalidates that the pinned continuation authority/revision is still current and not superseded by newer canonical authority. After the write it must read back the stable CURRENT and prove the intended generation, assignment-key, continuation-id, predecessor, authority and scope fields. A missing/different readback means the publication did not establish authority; the Role must not execute the new generation. Because the continuation command is deterministic, an overlapping PM/Role publication of the same authorized successor is idempotent; any different same-generation publication is a collision, never last-writer-wins authority. PM observing an eligible unrevoked continuation for terminal N must either publish/adopt that same continuation-id or rely on a newer canonical authority that invalidates the pinned continuation before issuing a different N+1; PM preference alone is not authority to race a different same-generation command.

**Scope fence.** Under this rule the Role may mutate only its own fixed CURRENT to publish that one N+1 successor, then execute it under normal Role ownership. It does not mutate `PM_EXECUTOR.md`, does not drain other lanes, does not use `QUEUE-PM-FAILOVER-001`, and gains no assignment-loop automation configuration authority. No scheduler mutation is required for this continuation because the Role is already running; if run budget prevents substantive N+1 execution after successful publication/readback, the next ordinary Role run consumes it.

**No capability chaining by the Role.** A self-published N+1 command may carry a further `continuation-authority` only if that further authority was already explicitly embedded/pinned in the prior PM-issued authority chain. The Role may not synthesize a new continuation block from its own result or from a newly discovered roadmap suggestion. Thus autonomous progress can follow a PM-preauthorized chain, but cannot expand its own authority.

**Failure semantics.** Missing/invalid continuation authority, incomplete command contract, ambiguous successor, user/external gate, independent-acceptance boundary, cross-lane choice, generation collision, or authority drift returns the lane to ordinary PM coordination; it is not a reason to invent work. Provider failure while publishing a fully authorized successor records an exact retry condition and is retried on a later Role run under `QUEUE-LOCAL-ISOLATION-001`.

## QUEUE-PM-FAILOVER-001 — Role-side emergency fenced PM surrogate drain
Role1 / Role2 / Role3 remain Role lanes by default and do not acquire PM write authority merely because they score PM poorly, are idle, or can see an obvious next action. Emergency takeover is permitted only through this rule and only as a short-lived surrogate PM lease on the existing `audit/assignments/PM_EXECUTOR.md` selector. Acquisition of that lease and recovery of an expired lease are the only exceptions to the ordinary `QUEUE-PM-EXECUTOR-001` requirement that the current active executor must already match before the selector itself may be changed; this exception grants authority to change/repair the selector only, and no other PM-owned control write is authorized until the new lease is read back exactly. The purpose is to recover control-plane forward progress, not to create a second permanent PM.

**Emergency propagation trigger — immediate path.** A Role must evaluate this path before ordinary score/cycle-based failover gating whenever its fresh Role controls, the bounded asynchronous Cursor-result relay check, or another compact control read exposes that substantive Role/Cursor progress is stopped, unclaimed, or unable to continue because a PM-owned transition has not been applied. This path does **not** require a low PM score, two Roles, two observation cycles, a prior scheduler-recovery attempt, or user intervention.

Emergency failover is confirmed by one fresh bounded confirmation scan when all of the following are true:
1. at least one Role or Cursor lane has executable or recoverable substantive work whose progress is presently blocked/stopped/unclaimed;
2. the blocking cause is a concrete PM-owned omission/failure such as an undrained terminal result, missing refill/dispatch, missing Cursor pickup/publication recovery, missing blocker route, stale PREPARED/Active reconciliation, or another mandatory transition already governed by `QUEUE-PM-DRAIN-001`;
3. current authority uniquely determines at least one safe PM-owned recovery action and no valid user pause, external wait, actor-owned in-progress execution, or higher-authority gate explains the stop; and
4. the fresh `PM_EXECUTOR.md` read shows no different unexpired failover lease already performing that recovery.

When these conditions hold, classify `PM_FAILOVER_REQUIRED` immediately. The Role does not finish an otherwise-idle/terminal normal path merely to emit a PM score first, does not wait for the next PM cycle, and does not end with explanation-only narration. It proceeds in the same run to fenced lease acquisition and, after exact lease readback, executes the surrogate PM drain. PM scoring may still be written as evidence, but it is diagnostic and must not delay emergency recovery.

A PM run that reported/explained a mandatory PM-owned transition without applying it is evidence of the omission, but repeated narrative failure is not itself required: the live blocked-lane + uniquely safe PM recovery proof above is sufficient on the first observed occurrence. Thus a PM-caused stop of Cursor A/B2 or a Role lane cannot remain dependent on an additional user command merely because ordinary score/cycle thresholds have not matured.

**Ordinary trigger confirmation — non-emergency path.** When the emergency propagation trigger is not confirmed, a Role may consider failover after finishing its normal Role-owned action/reconciliation and `ACTIVITY-PM-SCORE-001` score for the run. A cheap suspicion signal is either its just-authored PM score `<50/100`, or its lane has had two consecutive completed Role runs with no material work while the latest PM behavior did not establish a legitimate forward-work exhaustion/wait proof. Suspicion alone does not authorize takeover. Before acquisition the Role performs a bounded fresh confirmation scan of PM_EXECUTOR, PM automation health, the three Role CURRENT/OUTBOX pairs, and only the Cursor controls needed to decide whether PM has left recoverable work undispatched. When score corroboration is needed, it may exception-read only the latest relevant `PM_SCORE` entries from the fixed Activity stream; condition 1 below requires the same exact `observed-pm-run` identity when both entries carry one, and is unavailable rather than guessed when the two scores cannot be tied to the same PM observation window.

Ordinary failover is confirmed when at least one of these objective conditions is fresh and still unresolved:
1. two distinct Roles' latest scores for the same observed PM run/window are `<50/100`;
2. two consecutive PM/Role observation cycles show at least two lanes resting/waiting while a distinct safe executable forward action is already determined by current authority and no valid exhaustion/blocker proof exists;
3. the latest PM result/control state exposes `PM_DRAIN_INCOMPLETE`, `FORWARD_WORK_NOT_DISPATCHED`, `REFILL_MISSED`, or another explicit PM-owned drain/publication failure whose safe recovery action is already determined;
4. the PM scheduler is unhealthy under `QUEUE-AUTOMATION-HEALTH-001`, the governed recovery attempt did not restore a usable PM run, and safe PM-owned work remains.

Do not confirm failover for a legitimate `NEEDS_USER_INPUT`, user-directed pause/disable, external/vendor wait, another runtime that is currently and observably executing its owned work, a consumed terminal lane with no distinct safe next work, or any state where the fresh scan proves that no PM-owned action can advance the system. A low score caused only by missing evidence is not sufficient.

**Single candidate and lease acquisition.** Candidate priority is `Role2 -> Role3 -> Role1`. For the ordinary non-emergency path, a lower-priority Role may attempt acquisition only when every higher-priority candidate is disabled, unhealthy/stale beyond the applicable automation-health bound, explicitly declined/failed the same failover trigger, or is not due within the near-term wake window and would therefore leave the confirmed PM failure unresolved. For a confirmed **emergency propagation** trigger, do not wait for a future higher-priority wake merely to preserve preference: Role2 takes it when Role2 is the running eligible candidate; otherwise the next actually running eligible candidate in `Role3 -> Role1` may acquire immediately after the fresh selector fence. A later higher-priority Role must not preempt a valid unexpired lease. If PM_EXECUTOR already carries a well-formed unexpired failover lease, no other Role—including a higher-priority candidate—may acquire over it; it may only observe/wake the current lease owner or wait for governed expiry/release. This priority rule plus fresh selector fencing is the split-brain prevention path.

To acquire, the candidate fresh-reads `PM_EXECUTOR.md`, records the exact prior `active-executor`, `executor-instance`, and `epoch`, and writes the same stable selector with: `active-executor: CHATGPT_THREAD`; an executor-instance dedicated to that Role failover runtime (`CHATGPT_ROLE2_FAILOVER_E1`, `CHATGPT_ROLE3_FAILOVER_E1`, or `CHATGPT_ROLE1_FAILOVER_E1`); `epoch: <prior+1>`; `failover-role`; a deterministic `failover-lease-token` derived from the Role, prior epoch, and exact confirmed trigger identity (`observed-pm-run` or explicit PM failure/control identity), so overlapping copies of the same Role handling the same trigger converge on one lease identity; `failover-lease-until` no later than 30 minutes after acquisition; and the exact prior executor fields needed for restoration. The candidate must read back the selector and must not perform any PM-owned write unless the readback exactly matches its failover instance, new epoch, and lease token. Failure to establish that exact readback is a declined acquisition, not partial PM authority.

A failover run is fenced by all three values: executor-instance, epoch, and lease token. Before every PM-owned control mutation it fresh-reads `PM_EXECUTOR.md`; any mismatch, expiry, superseding user-directed executor switch, or missing lease token immediately ends its PM write path. Overlapping copies of the same Role failover runtime handling the same trigger therefore converge on the same deterministic lease token; a different token is a competing lease and must win the selector readback before the loser may write anything. Existing `QUEUE-DISPATCH-SAFETY-001`, `CORE-MONOTONIC-001`, and control readback requirements still apply to every dispatched generation.

**Surrogate PM scope.** After successful acquisition, the Role runtime temporarily acts as the active PM/control runtime, not as its ordinary Role lane. This changes the runtime actor mode only; it does not redefine or merge the Role lane responsibilities in `CORE-LANES-001`, and the Role lane remains a separately controlled work lane. It executes `QUEUE-FAST-001` and drains `QUEUE-PM-DRAIN-001` to a bounded fixed point across all safe Role/Cursor lanes, including `PM_DRAIN`, refill/next-work issuance, Cursor dispatch/pickup/publication recovery, blocker routing, publication/readback, and governed wakes/recovery that the active PM would normally own. In an emergency propagation run, the surrogate must perform every already-determined safe recovery transition exposed by that drain before reporting; explanation-only termination while such a transition remains is invalid. It may issue work to its own Role lane, but it must not execute that newly issued substantive Role assignment inside the same surrogate-PM section. It must not use failover to alter product/spec semantics, acceptance authority, Git write boundaries, user decisions, or any other authority that the PM itself does not possess.

**Release / crash recovery.** After a fixed-point drain, or sooner when no further safe PM action exists, the surrogate fresh-reads the selector and, only if its exact lease still owns it, restores the recorded prior `active-executor` + `executor-instance`, increments `epoch` again, removes/clears failover lease fields, read-backs the restored selector, and wakes/re-anchors the restored PM automation when allowed so the normal PM can reconcile promptly. A surrogate must not restore over a newer user/executor switch.

If the surrogate ends unexpectedly, any Role or the normal PM may treat an expired failover lease as stale only after fresh-read proves `failover-lease-until` has passed. Recovery restores the recorded prior executor with a new epoch before ordinary PM writes resume; if the recorded prior identity is missing/ambiguous, stop PM-owned writes and use `QUEUE-CONTROL-RECOVERY-001` rather than guessing. Failover acquisition/release/recovery are material Activity events authored by the Role runtime that performed them. PM score entries remain Role-authored and are never rewritten by the surrogate.

## QUEUE-AUTOMATION-001 — assignment-loop automation ownership
The active PM executor selected by `QUEUE-PM-EXECUTOR-001` is the configuration owner for the four dollworld assignment-loop automations: PM, Role1, Role2, and Role3. Narrow cross-loop scheduler operations explicitly authorized by `QUEUE-AUTOMATION-HEALTH-001`, `QUEUE-RESULT-WAKE-001`, and `QUEUE-CURSOR-RESULT-RELAY-001` are exceptions to configuration ownership; they may only toggle/re-anchor the already-known target loop as those rules permit and never change assignment authority.
Protocol Design must not proactively create/update/enable/disable/reschedule those automations merely because a protocol change suggests a prompt change.
Explicit user direction in the Protocol Design thread is sufficient authority to perform the specifically requested automation change there, provided current Role boundaries and the user's scope are preserved. Record a material change in continuity/control documentation when needed.

## QUEUE-AUTOMATION-SYNC-001 — prompt derivation / stale clause handling
Assignment-loop prompts are non-normative execution shells. They contain only stable actor/scheduler identity, one stable action selector, stable control/automation pointers, Rule ID references, and explicit scheduler pause-intent metadata required by `QUEUE-AUTOMATION-HEALTH-001`. They must not become a second copy of normative CORE/QUEUE/AUDIT/ACTIVITY rule bodies.
The stable action selector is launcher metadata only: the PM shell declares `Action=EXECUTE_PM_CONTROL_LOOP`, and each Role shell declares `Action=EXECUTE_ASSIGNMENT_LOOP`. A missing, empty, or mismatched action selector is prompt drift because the shell must unambiguously request execution rather than merely describe an actor or list authorities. The selector does not duplicate workflow semantics; all behavior remains owned by the referenced Rule IDs.
The PM loop's fixed declared runtime identity required by `QUEUE-PM-EXECUTOR-001` is included in the allowed stable actor/scheduler identity; selector epoch and all other live selector/task facts remain runtime-read only.
Live assignment facts do **not** belong in an automation prompt: generation numbers, task keys, current READY/WAITING state, current upstream result, expected task verdict, current user-decision facts, retry counters, fallback classifications, or other facts already owned by CURRENT/OUTBOX/Inbox/Active/PM_EXECUTOR must be read from those controls at run time. Dispatch/wake/recovery operations update live controls and schedule only; they do not rewrite prompts to mirror the new assignment or copy current recovery logic into the prompt.
When a normative rule change materially affects an assignment loop, the PM configuration owner reconciles only the stable Rule-ID/pointer shell before relying on stale wording. This reconciliation must not delay unrelated executable work when the stale text cannot misroute it. Any discovered live-task clause or general behavioral prose in a prompt is prompt drift and is removed rather than synchronized to another task state. A stale prompt clause never overrides live CURRENT/OUTBOX/Inbox/Active/PM_EXECUTOR or the current Rule ID owner.
Prompt reconciliation also applies `CONTROL-NONDUP-001`: compare all four canonical assignment-loop prompts against current Rule-ID owners and remove prose that materially restates/paraphrases a normative rule body. Allowed prompt prose is limited to actor identity, the fixed action selector above, fixed automation/control pointers, Rule-ID lists, and scheduler-only metadata that cannot be derived from Drive authority. A short label such as "apply QUEUE-CONTROL-RECOVERY-001" is allowed; a description of how that rule decides validity, generations, retries, failover, scoring, or publication is not.
The active PM performs a bounded prompt-shell drift check on the four canonical loops whenever (a) a protocol change alters a Rule ID used by those loops, (b) a loop prompt was edited, (c) a fixed control pointer intentionally changed, or (d) a run observes behavior that contradicts the Rule owner and prompt drift is a plausible cause. This is a trigger-based check, not a reason to reread full prompts on every unchanged run. Closure for any affected protocol/prompt change requires: owner MD updated first; affected prompt reduced to the allowed shell; semantic duplicate check against the active protocol root; and readback confirming no normative rule body remains duplicated in the prompt.
If a required behavior exists only in an automation prompt and has no normative owner text, do not delete it blindly. First classify it under the existing Rule-ID owner (or add a new Rule ID only when no existing owner fits), write the behavior exactly once in that owner MD, verify the owner change, then remove the duplicate prompt prose. This owner-first migration order is mandatory so prompt cleanup cannot erase behavior.
Protocol Design may identify and record prompt drift, but does not edit the four automations without authority under `QUEUE-AUTOMATION-001`.

## QUEUE-DISPATCH-WAKE-001 — post-dispatch Role wake acceleration
After the active PM successfully publishes and read-backs a **new executable** Role1/Role2/Role3 CURRENT generation, PM MUST perform the wake-eligibility check in the same PM run. When the target Role is eligible, PM MUST attempt a bounded wake-up reschedule rather than intentionally leave fresh work waiting for the Role lane's ordinary hourly slot. Failure of the scheduler optimization never invalidates the already-published assignment.

Wake-up rescheduling is an execution-latency optimization, not authority. `QUEUE-SCHEDULE-INDEPENDENCE-001`, CURRENT/generation identity, and normal Role reconciliation remain the correctness rules. The wake operation must therefore:
- apply only to a newly published executable generation, not `WAITING_UPSTREAM`, terminal state, a duplicate publication, or a Role lane already executing that generation;
- leave an intentionally disabled automation disabled; scheduler-health handling remains with `QUEUE-AUTOMATION-HEALTH-001`;
- before any wake schedule write, fresh-read the target automation and its scheduler health. If it is stale enough to qualify for `QUEUE-AUTOMATION-HEALTH-001`, perform/record that recovery first and do not use a wake reschedule to mask the stale scheduler; a wake-driven `updated_at` is not evidence that a scheduler-health reset occurred;
- if the target Role is already due to run within a short near-term window or has already picked up the new generation, avoid needless schedule churn;
- otherwise compute the wake slot from a fresh current local clock immediately before the automation update. Never publish a wake DTSTART that is already in the past or inside an ambiguous just-fired execution instant; choose the earliest safe future slot, normally about 1-3 minutes ahead and no later than about 5 minutes when a free slot is available;
- check the other dollworld assignment-loop schedules before choosing the slot and avoid intentionally placing two loops on the same minute; keep at least a small separation when practical. When several Roles are dispatched in one PM run, stagger them deterministically rather than allowing schedule-update order to collapse them onto one slot;
- re-anchor that same Role automation only; do not create a second one-off wake task. Preserve prompt, title, timing mode, timezone, enabled state, and `FREQ=HOURLY` recurrence. A successful wake re-anchors that Role's subsequent hourly cadence from the chosen slot until a later governed reschedule; no hidden second cadence exists;
- verify the updated automation state after rescheduling. A failed wake adjustment does not revoke the already-valid assignment; record/retry the scheduler optimization under the applicable automation/transient-failure rules while the pre-existing hourly schedule remains the fallback.

This rule standardizes the successful pattern of `publish assignment -> wake the owning Role promptly`, so an idle Role normally begins new PM-issued work within minutes instead of waiting up to the next hourly cadence.


## QUEUE-RESULT-WAKE-001 — terminal Role result wakes PM promptly
After Role1, Role2, or Role3 successfully publishes and read-backs a terminal OUTBOX result for its still-live assignment generation, that Role run must perform a bounded PM-wake check before normal exit. This is the reverse edge of `QUEUE-DISPATCH-WAKE-001`: a completed Role result must not sit until an arbitrary later PM polling slot when the PM loop can be safely woken within minutes.

The Role may perform only this scheduler operation on the PM automation; PM-owned Drive controls remain untouched until PM itself runs. Apply these guards:
- recheck CURRENT/OUTBOX identity first; do not wake PM for a superseded/cancelled/late generation that is no longer live;
- fresh-read the PM automation and use the known canonical PM automation ID;
- if PM is already running, has run after the terminal result, or is due in the immediate near-term window, avoid needless schedule churn;
- if PM is enabled and not imminent, re-anchor only that same PM automation to the earliest safe future slot, normally about 1-3 minutes ahead and no later than about 5 minutes when practical, preserving prompt/title/timing mode/timezone and `FREQ=HOURLY` recurrence;
- if PM is disabled, apply `QUEUE-AUTOMATION-HEALTH-001`: preserve an explicit user-directed pause, but recover an unexplained/accidental disable before attempting the wake;
- verify the automation state after the wake/recovery. Scheduler adjustment failure does not invalidate the terminal OUTBOX; record the exact retry condition while leaving the result consumable by the next PM run.

This wake is mandatory latency control for terminal `PASS`, `FIX_REQUIRED`, `BLOCKED`, cancellation/supersession completion, or any other terminal Role result that requires PM reconciliation. It does not by itself authorize the Role to choose or issue the next assignment. The only same-Role new-generation exception is the separately pre-authorized deterministic path in `QUEUE-ROLE-CONTINUATION-001`; that path derives authority from the consumed CURRENT, not from this wake rule or the terminal OUTBOX.


## QUEUE-CURSOR-RESULT-RELAY-001 — terminal Cursor/B2 result relay to PM
Cursor A and Cursor B2 can publish terminal Inbox/Active state without having direct scheduler authority. To prevent a terminal Cursor result from waiting for the PM loop's next ordinary hourly poll, each enabled Role1/Role2/Role3 automation acts as a bounded **read-only relay** for Cursor A and B2 result completion. This relay is scheduler infrastructure only and never grants a Role Cursor/PM assignment authority.

On each normal Role run, after its own CURRENT/OUTBOX handling and before normal exit, the Role performs a compact relay check using stable pointers to `CURSOR_INBOX`/`CURSOR_ACTIVE` and `B2_INBOX`/`B2_ACTIVE`:
- read the Active controls first; read the matching Inbox only when an Active control is terminal or otherwise indicates a completed/consumable result;
- if the terminal result finished after the PM automation's `last_run_time`, treat it as not yet observed by a subsequent PM run and wake PM under the same bounded scheduler mechanics used by `QUEUE-RESULT-WAKE-001`;
- if PM has run after the terminal timestamp but the matching Inbox/Active pair still exposes that same result as unconsumed/awaiting PM reconciliation, the Role may wake PM once more; do not infer consumption from PM `last_run_time` alone when the live pair still proves a mandatory transition;
- if PM is already running, due in the immediate near-term window, or the live Cursor/B2 pair is already consumed/superseded, do not churn the schedule;
- if PM is disabled/stale, apply `QUEUE-AUTOMATION-HEALTH-001` before the relay wake, preserving explicit `PAUSE_INTENT=USER_DIRECTED`;
- fresh-read PM automation state immediately before any update and verify the update afterward. Multiple Role relays observing the same result deduplicate by the PM run/due-time and live-control guards.

The Role never edits Cursor/B2 Inbox/Active, never decides the next Cursor task, and never interprets a terminal result as accepted merely by relaying it. PM remains responsible for consuming the result under `QUEUE-PM-DRAIN-001`. This rule exists only to close the asynchronous `Cursor/B2 terminal -> PM asleep` rendezvous gap using the already-existing assignment loops; it does not create a fifth automation or a second authority path.


## QUEUE-DISPATCH-SAFETY-001 — idempotent lane publication / no live-command overwrite
Before PM issues or replaces canonical work for a Role/Cursor lane, it reads that lane's live controls and establishes that the existing command is consumed/terminal, explicitly superseded/cancelled, or safely waiting such that the new command does not erase unrecorded work. A Role CURRENT whose matching OUTBOX is `WORKING`/missing for a genuinely started generation, or a Cursor ACTIVE task, is not an idle slot. Do not overwrite it with ordinary new work. User stop/cancel and explicit correction use their governed reconciliation path instead of silent replacement.
For a new command, prepare/verify prerequisite task authority/instruction/pointers first, then publish the lane command and read it back. Cursor A/B2 publication must pass the exact pre-`PREPARED` publication-integrity gate owned by `CURSOR-PUBLISH-001`; an observed `PREPARED + IDLE` state is reconciled through `CURSOR-PICKUP-001` before any wake/republication decision. If publication/readback is uncertain or interrupted, resolve the stable control identity and provenance before minting another generation/task. Same `(source-request-id, source-request-file-id)` dispatch is idempotent: a matching already-published command is reconciled, not duplicated.

## QUEUE-SCHEDULE-INDEPENDENCE-001 — scheduler jitter / overlap / authorization isolation must not change semantics
Minute ordering between the PM, Role1, Role2, and Role3 automations is an efficiency hint only; scheduler delay, jitter, overlapping runs, wake/re-anchor failure, or scheduler-only authorization state must not be relied on for correctness. Generation/task identity and owner-separated controls determine semantics.
Before PM mutates a lane it performs the fresh read required by `QUEUE-DISPATCH-SAFETY-001`. Before a Role publishes a terminal OUTBOX result, it rechecks that PM-owned CURRENT still names the same assignment-key/generation and has not been superseded/cancelled or replaced. If CURRENT changed while the Role was working, preserve the produced evidence but do not overwrite the OUTBOX as though the old generation were still the live command; reconcile the old work against the new state on the next bounded step. A late older-generation result never authorizes rollback of a newer PM generation.
No automation may classify another actor as idle/finished solely from the expected schedule order; use the current controls read in that run.

**Scheduler authorization/UI isolation.** Every assignment-loop schedule mutation governed by `QUEUE-PM-SELF-WAKE-001`, `QUEUE-DISPATCH-WAKE-001`, `QUEUE-RESULT-WAKE-001`, `QUEUE-CURSOR-RESULT-RELAY-001`, `QUEUE-AUTOMATION-HEALTH-001`, or another scheduler-only re-anchor/toggle is a latency/health optimization and never an authority prerequisite for already-valid Role/Cursor/PM work or result consumption. If the available scheduler mutation path would require a new interactive permission/consent UI, unavailable account approval, or another external authorization step, skip only that scheduler mutation, record the exact scheduler-only outcome (for example `WAKE_SKIPPED_AUTH` with the target loop/reason), preserve the existing enabled/hourly schedule unless an explicit user-directed pause already applies, and continue the substantive control drain/result publication. Do not create `NEEDS_USER_INPUT` / USER confirmation solely for scheduler authorization, do not downgrade an already-valid assignment/result to blocked, and do not route Google/Drive permission acquisition through product-authority/user-decision handling. Prefer a scheduler-local update path that does not require unrelated connector authorization.

## QUEUE-WORKING-RECOVERY-001 — Role WORKING interruption / overlap recovery
A same-generation Role OUTBOX `WORKING` state represents incomplete execution, not a permanent reservation. It records enough bounded recovery data to continue safely: assignment-key/generation, last-updated/start time, actual progress or completed outputs, exact next bounded step, and blocker/resume data when applicable. For work likely to cross an automation interval or take long enough that another scheduled run could overlap, publish `WORKING` early enough to expose the in-progress generation before continuing expensive work.
A later Role run seeing recent same-generation `WORKING` first avoids duplicate execution when a prior run may still be live. Before any OUTBOX replacement, apply `CORE-MONOTONIC-001`: an already-terminal same-generation OUTBOX wins over a late older `WORKING`/partial write. If `WORKING` survives beyond one expected Role cycle with no live-run evidence or fresh progress, treat it as an interrupted run: inspect the recorded progress/evidence, resume from the first incomplete bounded step, or finalize the result if the substantive work is already proven. Do not wait forever, restart the whole task, or mint a new generation solely because a prior Role run ended unexpectedly. PM continues to treat that lane as non-idle until the WORKING generation is reconciled, while independent lanes continue under `QUEUE-LOCAL-ISOLATION-001`.

## QUEUE-RUN-BUDGET-001 — action-before-optional-work under bounded runs
When a run has already determined a safe required control transition or substantive next action, perform and verify that action before optional reporting, activity-history reads, broad hygiene, nonessential handoff refresh, or speculative preflight. If tool/time/context budget becomes constrained, preserve the minimum authoritative mutation/evidence needed for forward progress first and defer optional narration/hygiene to a later run. A run must not consume its remaining budget documenting a transition it could still safely apply.

## QUEUE-CAPABILITY-DISCOVERY-001 — connector capability discovery before blocker
Lazy connector/tool exposure is not evidence that an authorized capability is unavailable. When a PM/Role assignment requires an in-scope connected action (including Drive read/search/fetch, raw-file update, lifecycle move, upload, folder operation, or equivalent control/evidence operation) and that action is not currently loaded, the runtime must first perform bounded connector resource discovery for the exact capability and invoke the discovered action when available.

A runtime must not report a tool/capability blocker merely because its initial tool surface omitted the required action. A capability blocker is valid only after bounded discovery was attempted and the required action is genuinely absent, permission-denied, unsupported for the target, or fails on invocation. Any such blocker records the attempted capability/action and concrete failure. For raw Markdown Drive controls, updates preserve the stable Drive file ID; lifecycle transitions move the same file identity rather than creating a second canonical copy. If an earlier run left an otherwise-determined transition unapplied solely because an unloaded action was mistaken for an unavailable capability, the next authorized run reconciles that stale state before unrelated new work.

## QUEUE-READ-COMPLETENESS-001 — complete reads before absence conclusions
A partial provider response is not evidence of absence. Folder/list/search pagination limits, provider-side top-N limits, response truncation, clipped text hydration, or an incomplete first page must not be used to conclude that a request/control/evidence file does not exist or that no executable item remains.
When correctness depends on an exhaustive set, use bounded provider pagination or an exact parent/identity query until the relevant set is complete. When correctness depends on full file content and the readable response is clipped, use the provider's full/raw fetch path. When a stable Drive file ID or canonical pointer is already known, fetch that identity directly before falling back to broad name search.
If the runtime cannot obtain a complete enough read after applying `QUEUE-CAPABILITY-DISCOVERY-001`, preserve live state and report the concrete provider/read limitation; do not convert incomplete visibility into `NOT_FOUND`, completion, rejection, or a user blocker.

## QUEUE-TRANSIENT-FAILURE-001 — transient infrastructure failure is retryable
Timeouts, rate limits, temporary connector/provider errors, incomplete sync visibility, and similar infrastructure failures do not change task/request semantics by themselves. Perform a bounded safe retry in the same run when useful. If the failure remains transient, leave the authoritative CURRENT/request/Inbox disposition unchanged, record the exact attempted operation and retry condition, and retry it on the next eligible run before unrelated queue hygiene.
Do not ask the user to resolve an infrastructure transient unless user action is actually required. Repeated failure may become an `EXTERNAL`/control-plane blocker only when the concrete provider failure is persistent enough to prevent the required action; it still must not be mislabeled as missing product/spec authority.

## QUEUE-CONTROL-RECOVERY-001 — fixed-control self-recovery
Fixed raw control files use stable identities. If a fixed CURRENT/OUTBOX/Inbox/request-control or `PM_EXECUTOR.md` is mechanically malformed, truncated, or left in an impossible partial-write state, do not invent a new task/generation or silently create a replacement canonical copy. First use the stable file ID, immediately prior valid revision when available, counterpart live controls, and current owner contract to determine whether one semantic-preserving repair is uniquely implied. Apply only that minimum repair and read it back.
For PM-owned controls, only the active PM executor may perform ordinary recovery. Special case: if `PM_EXECUTOR.md` itself is malformed but its stable file ID and immediately prior valid selector revision are available, the configured PM automation may restore that exact prior `(active-executor, executor-instance, epoch)` tuple only when its declared instance matches that prior selector. This is selector self-repair, not PM dispatch authority before the readback succeeds, and it does not increment `epoch`.
If more than one semantic state is plausible, fail closed on ordinary writes and escalate the exact ambiguity instead of guessing. Mechanical recovery must preserve already-completed results, consumed generations, and user stop/cancel instructions.
Legacy waiting controls created before `resume-watch` became mandatory are recoverable rather than permanently malformed. When the existing `resume-condition`, referenced authority/control, and live state uniquely identify the watched source, the active PM executor may add the missing `resume-watch` in place without minting a generation or reopening completed work. If the watched source is not uniquely inferable, keep only that item/lane waiting on the exact missing-watch ambiguity and continue unrelated work under `QUEUE-LOCAL-ISOLATION-001`. The same compatibility treatment applies to legacy `DEFERRED` / `NEEDS_USER_INPUT` PM requests through their PM-owned resolution section.
When a same-generation OUTBOX is missing/unreadable after a known result-channel write failure, check the matching actor fallback result and canonical evidence/output identity before redoing substantive work; recover the fixed OUTBOX when the fallback/evidence uniquely proves the result. A transport artifact named `TMP_ROLE<role>_G<generation>_OUTBOX_EGRESS` (or an explicitly equivalent same-generation egress artifact) is a recognized fallback result channel when its payload matches the live CURRENT assignment-key/generation and its immutable evidence/output pointers uniquely prove the terminal result. The active PM recovery path must discover and consume that egress before classifying the Role as `FAILED_NO_PROGRESS` or rerunning substantive work, copy the proven terminal payload into the fixed stable-ID OUTBOX, read it back, and then continue normal drain.

**Terminal result durability.** A Role run that has completed substantive work must not finish with only a detached result packet while its stable OUTBOX remains older. Result publication has a mandatory **egress commit barrier**: once the exact terminal state/result and immutable evidence packet are known, the next required control transition is the fixed stable-ID OUTBOX write/readback for that same assignment-key/generation. Packet creation is evidence staging only and is never terminal publication. Until the OUTBOX readback succeeds, the Role MUST NOT treat the run as complete, take a NO_ACTION/terminal fast path, perform scheduler re-anchor/disable work, or spend the remaining run budget on optional PM_SCORE/activity/reporting/hygiene ahead of the egress attempt. `QUEUE-RUN-BUDGET-001` applies with the OUTBOX egress transition as the first mandatory mutation.

If the fixed OUTBOX write cannot be established after bounded capability discovery/retry, before the run ends the Role MUST durably publish and read back either the exact `TMP_ROLE<role>_G<generation>_OUTBOX_EGRESS` payload or an equivalent governed same-generation recovery checkpoint containing assignment-key, generation, exact terminal state/result, immutable result/evidence pointer(s), and enough payload to reconstruct the fixed OUTBOX without redoing substantive work. The recovery channel is the mandatory fallback egress path, not optional cleanup. Only after canonical OUTBOX or that governed fallback has been read back may the Role append terminal activity/PM_SCORE evidence or return a terminal status. A scheduler invocation that produced a result artifact but established neither canonical OUTBOX nor a governed recovery channel is `RESULT_EGRESS_INCOMPLETE`, not a successful Role run; advancing `last_run_time`, creating a native Doc packet, or writing Activity evidence does not satisfy the barrier.

For historical/orphaned result packets created before this durability contract, PM may perform one bounded orphan-result recovery only when a unique immutable artifact itself contains the exact live assignment-key, generation, terminal state/result, and result payload/evidence; no conflicting same-generation result/fallback exists; and current authority proves the artifact belongs to that assignment. PM copies that exact proven terminal into the stable OUTBOX and records `recovered-via: QUEUE-CONTROL-RECOVERY-001`; it must not infer a verdict from narrative prose or broad title similarity. This orphan recovery is attempted before classifying the lane `FAILED_NO_PROGRESS`.

**PM egress convergence sweep.** On every active PM drain, any Role lane where logical CURRENT generation is newer than stable OUTBOX, or where a same-generation terminal artifact/fallback may exist, is not allowed to be classified solely from the stale OUTBOX. Before refill, idle, `FAILED_NO_PROGRESS`, or report, PM performs one bounded same-generation egress lookup using the canonical task/result pointers and governed recovery channels already exposed by CURRENT/OUTBOX/Activity/known task identity. If exactly one immutable terminal payload proves the live generation and no same-generation conflict exists, PM MUST converge that payload into the stable OUTBOX, read it back, and continue the drain in the same run. A PM run that observes a recoverable packet-only terminal state and exits without either canonical OUTBOX convergence or an exact concrete recovery blocker is `PM_EGRESS_RECOVERY_MISSED`, not successful drain. Broad Drive searching is not required when stable pointers already identify the result; discovery/read failures follow `QUEUE-CAPABILITY-DISCOVERY-001`, `QUEUE-READ-COMPLETENESS-001`, `QUEUE-TRANSIENT-FAILURE-001`, and `QUEUE-RETRY-BUDGET-001`.

After canonical CURRENT/OUTBOX has caught up beyond an unresolved `PM_REFILL_FALLBACK_V1` overlay, the active PM resolves that obsolete fallback comment; stale fallback overlays must not accumulate as live logical commands once raw canonical control has superseded them.


### PM raw-CURRENT transport fallback overlay
If the active PM has already determined the exact next Role assignment but canonical raw `ROLE*_CURRENT.md` replacement fails after the bounded `update_file` retry paths with a concrete file-transport error such as `BLOCKED_FILE_REFERENCE`, PM may use a **Drive comment attached to that same stable CURRENT file** as a temporary command overlay. This is a transport fallback only; it does not change Role ownership, task semantics, generation ordering, or the stable CURRENT file identity.

A valid unresolved fallback comment begins with `PM_REFILL_FALLBACK_V1` and contains at minimum: `executor-instance`, `executor-epoch`, `role`, `assignment-generation`, `assignment-key`, `previous-assignment-generation`, `state`, exact bounded `work-now`, expected `terminal`, source/predecessor pointers, forbidden scope, and `created-at`. The PM writes it only after fresh-reading `PM_EXECUTOR.md`, the stable CURRENT body, and the matching terminal OUTBOX. For a normal refill, `assignment-generation` must be exactly one greater than the logically current completed generation; it must never jump over an unconsumed executable generation.

The **logical CURRENT** for a Role is the higher of: (a) the canonical CURRENT body; or (b) the single newest unresolved valid `PM_REFILL_FALLBACK_V1` comment on that same stable CURRENT file. A fallback comment is valid only when all of the following hold:
- its `executor-instance` and `executor-epoch` match the live PM selector that authorized the write;
- its Role and stable-file identity match the Role being polled;
- its predecessor generation is already terminal/consumed by the PM when the comment was issued;
- its generation is monotonic relative to the body, OUTBOX, and any earlier valid overlay;
- no newer canonical CURRENT body or newer valid overlay supersedes it;
- its command is bounded by current authority and would have been a valid ordinary CURRENT write.
If multiple unresolved comments conflict for the same next generation, or selector/generation identity cannot be proven, fail closed and do not execute either command.

Role automation reads CURRENT comments only when ordinary body/OUTBOX reconciliation shows the body cannot represent the newest logical command (for example terminal OUTBOX equals the body generation while PM refill is transport-blocked, or OUTBOX is behind a newer valid overlay). When a valid overlay exists, the Role treats it exactly as the PM command for execution/reconciliation purposes and writes normal same-generation OUTBOX evidence. The Role never edits or resolves the PM fallback comment and never uses arbitrary comments as authority.

PM may continue multiple generations through this fallback while raw transport remains unavailable: after overlay generation N becomes terminal and is freshly consumed, PM resolves/supersedes the prior overlay and may issue exactly one next valid N+1 overlay. At most one executable unresolved fallback overlay per Role may exist. PM reporting must show `FALLBACK_OVERLAY_DISPATCHED` rather than `REFILL_WRITE_BLOCKED` when the overlay was successfully written and read back through `get_file_comments`.

For generation arithmetic and NO_ACTION decisions, actors use the **logical consumed generation**, not merely the raw CURRENT body. The logical consumed generation is the newest generation whose terminal result is proven by either the canonical OUTBOX body or a single valid same-generation governed OUTBOX/result recovery checkpoint that was written and read back under this rule. A stale raw CURRENT/OUTBOX body may therefore lag the logical state after transport failure. Before issuing or executing generation N+1, the actor must prove N is the newest valid logical consumed generation and that no executable unresolved N+1 overlay or conflicting recovery state already exists. Duplicate issuance caused by falling back to an older raw body is a control-recovery defect and the duplicate command must be cancelled/superseded rather than executed.

A fallback publication/result is not considered closed merely because a comment/checkpoint write call returned success. The writing actor must read back the same stable control's comment/checkpoint and verify role, executor/epoch where applicable, generation, predecessor, command/result identity, and non-conflict. Only after that readback may it be used as logical CURRENT/terminal state. Failed or ambiguous readback remains a transport/recovery failure; do not silently treat the older raw body as the latest state.

When raw CURRENT replacement becomes available again, PM materializes the newest logical CURRENT state into the stable raw CURRENT body, fresh-reads it, then resolves obsolete fallback comment threads. If the newest overlay generation already terminalized, PM may materialize the next governed logical CURRENT directly, provided all intervening overlay generations and OUTBOX results are explicitly consumed and monotonicity is proven. Fallback comments are transport evidence/control overlays, not historical task artifacts, and are resolved after canonical-body convergence.

## QUEUE-LOCAL-ISOLATION-001 — local failure/blocker must not abort independent work
A failure or blocker is global only when its dependency actually spans the control plane, such as an unreadable/ambiguous PM executor selector that prevents ownership determination, a shared Git/index condition that affects all intended Git writers in the same environment, or a genuinely project-wide authority ambiguity. A malformed individual PM request, one lane's control read/write failure, one user gate, one external dependency, one evidence transport failure, or one blocked task is local by default.
PM isolates the affected request/lane, records the exact retry/resume condition, and continues the compact scan and safe actions for independent lanes in the same run. A local failure must not cause an early return before already-visible independent mandatory transitions are handled. An individually malformed request may be left non-terminal with an exact parsing/identity question or safely rejected only when its immutable intent cannot be recovered; it never prevents processing other requests.

## QUEUE-STALL-RECOVERY-001 — control-plane starvation detection / priority recovery
A control state that should have transitioned but survives a completed active-PM cycle without an applied transition or exact blocker is a control-plane stall, not ordinary idle. Stall candidates include: a terminal Role OUTBOX with the same generation still exposed as `READY`; a discovered `PENDING` PM request left unresolved; a satisfied `resume-watch` still left waiting; a consumed PREPARED command not reconciled; a terminal request left in inbox after its lifecycle move should have completed; and a Cursor PREPARED command left unclaimed beyond `CURSOR-PICKUP-001`.
On the next active PM run, reconcile stall candidates before ordinary new issuance and before optional reporting/hygiene. Do not require a user message to wake a machine-observable stall. If recovery still cannot complete, write the exact retry/blocker instead of silently carrying the stale state forward. Local stall recovery follows `QUEUE-LOCAL-ISOLATION-001`, so one stalled lane does not freeze other safe work.

A Role loop can be scheduler-healthy yet execution-stalled. `ROLE_LOOP_NO_PROGRESS` is therefore a cross-control observation, but it is deliberately fail-safe against schedule races and long-running work:
1. Detection is active only when live Role CURRENT is executable and its assignment-key/generation is newer than the represented Role OUTBOX. A valid `WAITING_UPSTREAM`, `SUPERSEDED`, consumed terminal generation, or same-generation material `WORKING`/progress checkpoint is not a no-progress candidate.
2. PM uses the Drive file metadata `modifiedTime` of the live CURRENT publication as the visibility boundary. A Role automation run is eligible evidence only when its current `last_run_time` is strictly later than that CURRENT `modifiedTime`. Embedded prose timestamps such as `updatedAt` are not sufficient for this ordering test. A Role run that started or completed before the CURRENT became visible cannot be counted against that generation.
3. After an eligible Role run, PM fresh-reads CURRENT and OUTBOX. Classify one `ROLE_LOOP_NO_PROGRESS` occurrence only when the same executable generation is still exposed and there is no same-generation terminal result and no materially newer same-generation `WORKING`/progress/blocker checkpoint. Mere scheduler `last_run_time` movement is not material progress.
4. The first occurrence is persisted on that same PM-owned Role CURRENT as recovery metadata, without changing the assignment identity or work contract: `stall-recovery-generation`, `stall-recovery-count: 1`, `stall-recovery-observed-role-last-run`, `stall-recovery-observed-at`, and `stall-recovery-wake-issued-at`. These fields are recovery bookkeeping only, not Role authority. PM then performs at most one governed near-term Role re-wake for that exact generation. If another rule (`QUEUE-DISPATCH-WAKE-001`, `QUEUE-PM-SELF-WAKE-001`, `QUEUE-AUTOMATION-HEALTH-001`, or `QUEUE-RETRY-BUDGET-001`) has already issued a wake/re-anchor for the same Role, generation, and observed `last_run_time`, that wake satisfies this occurrence; do not issue a duplicate scheduler nudge under a second Rule ID.
5. On a later PM run, a second occurrence exists only if the persisted `stall-recovery-generation` still matches the live generation, the Role automation has a strictly newer eligible `last_run_time` than `stall-recovery-observed-role-last-run`, and fresh CURRENT/OUTBOX still show no same-generation material movement. Then increment `stall-recovery-count` and promote the lane to persistent Role runtime/control stall. Route root-cause recovery before relying on further hourly polling; repeated schedule nudges without substantive movement are containment, not progress.
6. **Control-plane run success is fail-closed.** An eligible Role scheduler invocation is never treated as successful merely because `last_run_time` advanced or the automation provider reports a completed invocation. For a newer executable CURRENT generation, success requires one of these externally observable postconditions after the governed completion-grace window: (a) matching same-generation terminal OUTBOX; (b) matching same-generation material WORKING/progress/blocker checkpoint; or (c) PM-owned reconciliation has made that generation non-executable for an independently valid reason. If none exists, persist `role-run-verdict: FAILED_NO_PROGRESS` plus the observed eligible `last_run_time`; user-facing PM status for that lane is failure/recovery, not ordinary wait.
7. The first `FAILED_NO_PROGRESS` occurrence may receive the single bounded re-wake from item 4. A second eligible `FAILED_NO_PROGRESS` for the same generation **must not** be handled by another blind schedule nudge. PM immediately applies `QUEUE-BLOCKER-ROUTE-001` / `CORE-AUTH-001`: if the substantive work can be performed by another currently authorized non-conflicting lane/executor without weakening an independence requirement, dispatch the same bounded work/evidence directly to that alternate lane and record the failover provenance; the failed Role scheduler is no longer the sole progress path. If the task has an exclusive semantic owner or independent-acceptance requirement that forbids substitution (for example a Role1-only Sprint transition certificate), do not impersonate that owner and do not mark WAITING_UPSTREAM. Persist `BLOCKED_EXECUTOR_UNAVAILABLE` / `ROLE_EXECUTOR_PERSISTENT_NO_PROGRESS` with the exact generation and failed invocation evidence, keep independent lanes running, and surface the blocking executor failure as RED until an authorized executor is restored.
8. PM must not advance a gate, consume a Role result, or claim progress from a scheduler invocation whose only evidence is provider completion/`last_run_time`. The proof boundary is the matching CURRENT/OUTBOX/checkpoint state. This postcondition applies equally to manual recovery wakes and ordinary hourly Role runs.
9. Reset/remove the stall-recovery and `role-run-verdict` metadata when any of these happens: the generation changes; same-generation terminal OUTBOX arrives; a materially newer same-generation WORKING/progress/blocker checkpoint appears; CURRENT becomes non-executable for an independently valid reason; or PM supersedes/reconciles the generation. Reset is a mechanical PM-owned control cleanup, not a new assignment.

The **completion-grace window** exists only to avoid misclassifying a still-running Role invocation. It is not permission for an unchanged executable generation to survive indefinitely: PM uses the already-governed short follow-up cadence from `QUEUE-PM-SELF-WAKE-001` and evaluates the postcondition on the first follow-up at least about 5 minutes after the eligible `last_run_time` unless a same-generation terminal/checkpoint arrives sooner. A Role that needs more than one run must make same-generation material progress visible through the checkpoint contract from `QUEUE-RECONCILE-001` / `QUEUE-WORKING-RECOVERY-001`; unchanged heartbeat/scheduler metadata alone never counts as progress.

This rule does not create work, override a valid wait, re-run an already terminal generation, or weaken independent acceptance/semantic ownership merely to avoid an executor failure. It converts silent/no-op invocations into explicit control-plane failure and removes repeated no-op scheduler runs as the sole progress mechanism.

## QUEUE-AUTOMATION-POINTER-001 — stable cached pointers for assignment-loop reliability
Assignment-loop automation shells may cache stable Drive file/folder IDs for fixed compact controls and request inboxes so normal runs do not depend on global title search. Cached IDs are non-normative execution pointers, not authority: each direct read verifies the expected title/purpose/MIME/actor identity, and current Rule-ID owners still define semantics and placement.
If a cached ID is unreadable, deleted, or resolves to the wrong identity, the runtime falls back to the canonical Rule owner plus `QUEUE-CAPABILITY-DISCOVERY-001` / `QUEUE-READ-COMPLETENESS-001`; it must not silently conclude that the control/request set is absent. An intentional canonical fixed-ID replacement is a material automation-pointer change and triggers `QUEUE-AUTOMATION-SYNC-001`.

## QUEUE-WATCH-POLL-001 — machine-observable waits must actually be polled
`resume-watch` is an execution pointer, not descriptive prose only. For every non-terminal Role wait or PM request whose resume source is machine-observable, PM must know what source to read and when it is next due. New waits should express a compact `watch-kind`/target through the `resume-watch` value (for example a stable control/file ID, canonical lane control, or external condition key) and may add `watch-cadence` / `next-check-at` when checking every PM run would be wasteful. Internal compact-control watches default to every active PM run unless a safer cadence is stated.
When a watch is due, PM reads the watched source directly even if the waiting request/control file itself did not change. A machine-observable wait must not require a user message to wake it. Legacy free-form `resume-watch` remains valid when the watched source is uniquely inferable; otherwise repair it under `QUEUE-CONTROL-RECOVERY-001`. Watch-source read failures follow `QUEUE-TRANSIENT-FAILURE-001` and `QUEUE-RETRY-BUDGET-001`.

**Satisfied-wait closure is mandatory and cross-run.** Every active PM run must re-evaluate each Role CURRENT in `WAITING`, `WAITING_UPSTREAM`, or equivalent non-terminal watch state whenever its internal watch is due or current compact evidence already proves the resume condition. If the watched condition is satisfied, the wait is stale and must not survive the drain unchanged. PM must, in the same drain cycle, publish/read back the executable Role state: normally transition the same unconsumed generation to `READY` when the assignment body already fully defines the pending work, or otherwise publish the exact next generation required by the owner rule. Then perform `QUEUE-DISPATCH-WAKE-001` subject to `QUEUE-SCHEDULE-INDEPENDENCE-001`. A satisfied wait left unchanged after PM observed the terminal watched source is `WAIT_RESUME_MISSED_RECOVERY` and a `QUEUE-STALL-RECOVERY-001` defect.

A Role automation that independently observes its own `resume-watch` as satisfied may proceed with the already-authorized unconsumed generation when the CURRENT body defines the work and no PM-owned mutation is needed; it must not remain `NO_ACTION` solely because the persisted state label still says `WAITING_UPSTREAM`. If a state normalization is required for unambiguous execution, it requests/executes the PM-owned recovery rather than inventing a new task.
`USER` is used only for genuinely non-machine-observable input. If the exact user answer is supplied in a non-PM dollworld thread, that thread submits a `USER_INPUT_RESPONSE` PM request with `responds-to: <request-id>` (and target file ID when needed) rather than assuming the designated PM runtime can see another thread's reply. A reply received directly by the active PM runtime may resolve the waiting request without creating a second request.

## QUEUE-REQUEST-LIFECYCLE-001 — strict request disposition / storage closure
Semantic request resolution values are exactly the set governed by `QUEUE-EXTERNAL-REQUEST-001`: `PENDING`, `DISPATCHED`, `DEFERRED`, `REJECTED`, `DUPLICATE`, `NEEDS_USER_INPUT`, or `SUPERSEDED`. `PROCESSED` is a storage/lifecycle concept, not a semantic resolution value; composite values such as `SUPERSEDED / PROCESSED` are invalid for new writes.
Before PM exits, a request with terminal semantic disposition (`DISPATCHED`, `REJECTED`, `DUPLICATE`, `SUPERSEDED`) must be in processed storage, or the same request must carry an exact lifecycle-move failure/retry record. A terminal request silently left in the non-terminal inbox is a `QUEUE-STALL-RECOVERY-001` candidate. Legacy/custom `PROCESSED` wording is normalized without redispatch: if canonical dispatch provenance proves work was issued, normalize to `DISPATCHED`; if it was superseded/rejected/duplicate, normalize to that exact terminal disposition; then complete the physical move. Never infer a new dispatch merely to make lifecycle wording fit.

## QUEUE-RETRY-BUDGET-001 — transient failure cannot retry forever silently
A retryable provider/control operation records enough compact continuity to distinguish a fresh transient from a persistent stall: operation/target, first failure, latest failure/error, and consecutive eligible retry count when the failure spans runs. Same-error transient recovery uses bounded same-run retry plus later-run retry under `QUEUE-TRANSIENT-FAILURE-001`.
After three consecutive eligible runs fail on the same required operation without progress, classify it as a persistent control/external blocker for the affected item, preserve the next retry condition, and surface the concrete failing capability/provider path. Do not keep calling it an ordinary transient forever. The blocker remains scoped under `QUEUE-LOCAL-ISOLATION-001`; unrelated lanes continue. If a different route/capability can safely satisfy the same operation, try that bounded alternative before user escalation.
For a PM-selected **optional preferred helper/evidence lane** whose pickup/consumer failure already has a safe alternate route, use the stricter bounded fallback policy: at most two governed pickup/recovery attempts and no more than 30 minutes from the first confirmed pickup/executor failure. Scheduler wakes, heartbeats, re-reads, and same-byte refreshes do not reset that budget. On the second failed attempt or wall-clock cap, classify `PREFERRED_LANE_RETRY_EXHAUSTED` and select the safe alternate route in the same PM drain. Optional independence may degrade only when the task authority permits it; record `INDEPENDENCE_DEGRADED_FALLBACK` and any required later re-audit. This clause does not authorize moving production work to a lane that lacks production authority.

## QUEUE-FAIRNESS-001 — no silent lane starvation
Urgent user stop/cancel, correction/supersession, active critical-path recovery, and material safety blockers may legitimately outrank other work. Outside those cases, PM must not repeatedly spend entire cycles on one request/lane while another lane has already-known safe executable or mandatory reconciliation work. Every active PM run performs at least the compact live-control scan needed to detect mandatory transitions for all Role lanes and relevant Cursor/B2 lanes before normal exit, even when the PM-request inbox is large.
A lane with known safe executable work or an already-determined mandatory transition may not be skipped through normal PM completion even once. If such work remains undispatched at the final scan, the run is `PM_DRAIN_INCOMPLETE / FORWARD_WORK_NOT_DISPATCHED`; PM continues the fixed-point drain or records the concrete higher-priority dependency/collision/capability blocker that prevents dispatch. Repeated-cycle starvation detection remains useful for diagnosing persistent control failures, but it is not a grace period that permits the first or second missed dispatch. This rule does not create busywork and does not override `CORE-LANES-001`; it prevents attention/backlog ordering from becoming an accidental stop condition.

## QUEUE-AUTOMATION-HEALTH-001 — assignment-loop scheduler continuity
The four assignment-loop automations (PM, Role1, Role2, Role3) are execution infrastructure, not authority. Scheduler stops are treated as an expected recoverable failure mode. This rule does **not** rely on a stopped actor obeying a prohibition before it stops; continuity is provided by the surviving canonical loops.

**Canonical four-loop mutual recovery.** Every surviving PM / Role1 / Role2 / Role3 run performs one bounded scheduler-health check before normal exit across the other three canonical loop IDs (and may include itself for readback only). For each target loop:
- if `is_enabled=true`, leave it enabled; re-anchor only when another existing wake/recovery rule requires a near-term run;
- if `is_enabled=false` and the target prompt shell carries `PAUSE_INTENT=USER_DIRECTED`, preserve the user pause and do not revive it;
- if `is_enabled=false` and no explicit user pause marker exists (`PAUSE_INTENT=NONE` or equivalent no-pause state), classify `UNEXPECTED_CANONICAL_LOOP_STOP` and the surviving actor is explicitly authorized to set that **same existing automation** to `is_enabled=true`, re-anchor it to the earliest safe future slot (normally 1-3 minutes, no later than about 5 minutes when practical), preserve prompt/title/timing mode/timezone and `RRULE:FREQ=HOURLY`, then read back the target automation;
- do not create a replacement/duplicate automation. Recovery uses only the four existing canonical loops.

This recovery authority is symmetric: PM may recover Role1/Role2/Role3; Role1 may recover PM/Role2/Role3; Role2 may recover PM/Role1/Role3; Role3 may recover PM/Role1/Role2. It is a narrow scheduler operation only and does not transfer assignment, audit, verdict, or Drive-control authority between actors.

**Blocker does not end scheduler continuity.** A Role or PM may still be unable to perform its assigned substantive work because a control file, Drive ID, provider surface, Cursor path, permission, or other dependency is unavailable. That condition may be recorded as `BLOCKED` for the work, but it does not authorize disabling the loop. More importantly, continuity does not depend on that actor honoring this sentence: if it disables anyway, one surviving canonical peer must restore it under the mutual-recovery rule above. The actor should route/recover/continue independent safe work under `QUEUE-BLOCKER-ROUTE-001`, `QUEUE-CONTROL-RECOVERY-001`, `QUEUE-CAPABILITY-DISCOVERY-001`, `QUEUE-ROLE-AUTONOMY-001`, and `QUEUE-PM-DRAIN-001` as applicable.

**Explicit pause is the only non-recoverable disabled state.** A target loop is intentionally left disabled only when its own prompt shell contains `PAUSE_INTENT=USER_DIRECTED`, representing an explicit user-directed pause for that specific loop. A generic blocker, `WAITING_UPSTREAM`, `IDLE`, `DEFERRED`, terminal/consumed state, no-work result, repeated read failure, or desire to avoid hourly retries is never equivalent to a user pause.

**No separate watchdog.** This is not a fifth watchdog automation or host supervisor. Mutual recovery piggybacks on the already-existing PM/Role hourly runs. If at least one canonical loop survives, it can restore any subset of the other three stopped loops. If all four canonical loops are simultaneously disabled, same-scheduler recovery is impossible and is not claimed.

**Recovery verification.** Scheduler recovery is proven only by an observed incident sequence: target canonical loop becomes disabled without `PAUSE_INTENT=USER_DIRECTED`; a different surviving canonical loop subsequently observes that state and re-enables/re-anchors the target; target then records a later `last_run_time`. Manual human/chat repair does not count as proof. A surviving peer that runs after an unexpected stop and leaves that target disabled is `CANONICAL_LOOP_RECOVERY_MISSED`.

## QUEUE-REPORT-001 — PM user-facing control status report

**Report eligibility fence — post-action state only.** PM may enter the user-facing report path only after `QUEUE-PM-DRAIN-001` has reached a fresh bounded fixed point and every already-observed safe PM-owned transition has either been applied and read back or has a concrete non-PM blocker/retry condition. The report describes the **post-action state**; it must never be used as a planning surface for PM work that remains executable in the same run.

A report is invalid and PM must return to the drain before showing it if any row, including PM / Role / Cursor rows, contains a `next`, `次の扱い`, `次の動き`, `needed`, `必要`, `継続`, or equivalent field whose substance is an action still owned and executable by the active PM or surrogate PM. Examples include `control drain継続`, `canonical ROLE2_CURRENT をG346へ更新必要`, `publication recovery`, `pickup/dispatch/refill needed`, `blocker route needed`, or `re-evaluate B2 progress` when the required evidence/recovery reads are available in the run. Those are execution instructions, not reportable next steps. PM performs them first, reads back, re-scans, and only then renders the resulting state.

A PM row may not report `control drain継続`, `drain pending`, `reconciliation needed`, or equivalent while the drain is still internally executable; the presence of such wording is itself proof that report eligibility was not reached. A Role/Cursor row may show a future next action only when that action belongs to a genuinely external/user dependency, an actor currently executing its own claimed work, a machine-observable wait already armed by PM, or another non-PM owner. When a PM-owned action cannot be completed because of a concrete provider/tool failure, the row must show the attempted action plus exact blocker/retry condition, not merely `必要`/`継続`.

Before rendering the table, PM performs a final **actionability lint** over the candidate report: for every proposed `次の扱い/次の動き`, ask `Can the active PM safely do this now from current authority and available controls?` If yes, suppress the report, execute that action under `QUEUE-PM-DRAIN-001`, read back, and regenerate the report from fresh state. This lint is mandatory but bounded; it does not authorize speculative work or new semantics.

**Execution-phase classification lint.** PM must not attach an active-execution health label to a lane whose authoritative Cursor state is already terminal. In particular, `B2_PROGRESS_UNPROVEN` is reportable only while the same B2 task is still claimed as `INVOKING`/equivalent substantive execution and the required child/process or task-scoped progress evidence is missing/stale. If the B2 task is already terminal `BLOCKED`/completed, Active is no longer executing, no verification child exists, and the SDK executor is healthy/idle, the row must classify the terminal result and executor-idle state separately; it must not describe that lane as progress-unproven or imply an ongoing Cursor execution failure. Terminal result semantics dominate stale/irrelevant active-progress diagnostics.

**Owner-attribution lint for Cursor publication.** PM must preserve the ownership boundary from `CURSOR-LOCK-001` / `CURSOR-PUBLISH-001` / `CURSOR-PICKUP-001` in user-facing wording. A local/canonical instruction existing while the PM-owned Inbox remains `LOCAL_MIRROR_PENDING`, non-`PREPARED`, or otherwise not claimable is a PM publication/reconciliation condition until the governed publication gate is closed; it is not ordinary Cursor waiting and must not be phrased as though Cursor A must make claimability true. If executor health is normal and it correctly refuses a non-`PREPARED` Inbox, report the executor as healthy/idle and attribute the unresolved state to the PM-owned publication transition (or to the exact missing reconcile capability when that is the factual blocker). Wording such as `claimability成立後にA起動` is insufficient when the missing claimability is itself PM-owned; the row must name the owner and whether PM has already executed or is blocked from the required publication/reconcile action.
Every scheduled PM run and every user-triggered PM control run (including `k` / `ｋ`) that emits any user-visible output MUST begin with the exact summary header shape `PM run　🟢稼働 X / 🟡待機 Y / ⚪休止 Z / 🔴停止 N`, followed immediately by one compact status table. This format is mandatory regardless of whether the run primarily performed control mutation, blocker recovery, capability discovery, scheduler repair, reconciliation, or explanatory follow-up; PM may not substitute a narrative-only, reduced-column, prose-summary, or alternate table format. The required columns are `担当 / 稼働 / 現在の仕事 / CURRENT G / last_run / OUTBOX G / progress / verdict / 次の動き`. Cursor lanes may use `—` for generation/run fields that do not apply, but Role1/Role2/Role3 must populate all five execution-proof fields from fresh controls/automation state. Additional concise narrative may appear only after the required header and table.

For every Role row, PM must show:
- `CURRENT G`: current assignment generation plus executable state (`READY`, `WORKING`, `WAITING_UPSTREAM`, etc.);
- `last_run`: the Role automation `last_run_time` observed in the same PM scan, rendered in local time when practical;
- `OUTBOX G`: represented OUTBOX generation and terminal/nonterminal state;
- `progress`: concise same-generation material evidence (`terminal`, `WORKING`, concrete progress/blocker checkpoint, `none`, or `not-applicable`);
- `verdict`: machine classification derived from current controls and the applicable queue rules, not from scheduler activity alone.

A Role automation `last_run_time` advancing is never itself progress. When `QUEUE-STALL-RECOVERY-001` classifies an eligible completed Role run with no same-generation terminal OUTBOX and no material same-generation WORKING/progress/blocker checkpoint as `FAILED_NO_PROGRESS`, the user-facing row must show `🔴 停止中` and verdict `FAILED_NO_PROGRESS`; it may not be softened to `🟡 待機中`, `実行済み`, `起動済み`, or ordinary scheduler delay. During a valid in-flight completion grace, report `🟢 作業中` or `🟡 待機中` only as justified by the authoritative state and label the verdict `IN_FLIGHT_GRACE`, never success.

If CURRENT and OUTBOX are already same-generation terminal, that generation is consumed. After the bounded next-work check in `QUEUE-PM-DRAIN-001`, report `TERMINAL_CONSUMED` / `⚪休止` when no distinct safe assignment or useful watched dependency exists; do not create a new generation just to make the display look idle. If a concrete safe next assignment exists and PM fails to publish it, that is a drain/action-closure failure under `CORE-ACTION-001` / `QUEUE-PM-DRAIN-001`, but the failure is the missed real work, not stale CURRENT wording itself. If CURRENT is legitimately non-executable (`WAITING_UPSTREAM`, `SUPERSEDED`, etc.), classify from that state and do not fabricate a no-progress failure.

**Generation-dominant presentation.** For human-facing status, the newest valid logical CURRENT generation/state is the primary current-state display. OUTBOX is result/history for the generation it represents, not an independent current blocker when it is older than CURRENT. If `CURRENT G > OUTBOX G`, PM MUST label the OUTBOX entry as prior/history (for example `prior G302 BLOCKED`) and MUST NOT carry an older OUTBOX `owner: USER`, blocker, verdict, or wait label into the row's current `稼働`, `verdict`, or `次の動き` unless current authority explicitly re-establishes the same blocker for CURRENT. When an older USER wait has been withdrawn/reconciled, report it as historical/withdrawn rather than as the active blocker. If logical fallback/recovery state is newer than the raw body, display the logical generation and mark the raw body as lagging/recovery state as required by `QUEUE-CONTROL-RECOVERY-001`.

`WAITING_UPSTREAM` is waiting, not resting; a material `BLOCKED` state or persistent executor/control failure is stopped, not ordinary waiting. Keep narrative follow-up concise and action-oriented.
